# Deslop baseline — 2026-10-04

Measured with an isolated headless Chrome (visible state, 1920x1080, DPR 1) driven over CDP,
sampling profiler at 0.5 ms, symbolicated through `dist/app.js.map`. The in-session Chrome tab
reports `visibilityState: hidden`, which throttles timers and rAF to ~1 Hz — never measure there.

Interaction script: 15–20 s of repeated wheel zoom (price), shift-wheel (time) and 30-step drags
over the heatmap canvas, against the live server on :8787 (4 default venues, empty browser profile).

| Build / mode | frame p50 | frame p95 | notes |
| --- | --- | --- | --- |
| Original, cross-tab "native" cache mode | 133 ms | 184 ms | ~7 fps on a nearly empty chart |
| Same build, `navigator.locks` removed (tab-local mode) | 16.7 ms | 16.9 ms | the app's own fallback path |
| After default scope flip (`browserCacheScope`) | 16.8 ms | 66–83 ms | `?acceptance=1` makes no difference |

## The heatmap was empty because the server refused to serve history

`GET /api/history/heatmap?...&depthBands=20&wire=hlm-observed-history-v1` returned **503**:

```
physical-rss-reservation-hard-limit  requestedBytes 761,423,908  hardLimitBytes 268,435,456
```

`estimateDepthBandResponseBytes` stacks per-cell coefficients ("32x parsed JSON, 4x text, 2 KiB
cells ...") into a ~760 MB bound for a response of a few KB. The identical request without
`depthBands=20` returned 200 in ~370 ms. `sendJsonWithTransientReservation` now builds, bounds
the body size and sends; the reservation layer is gone.

After that fix the old client still never painted history: it requested ever coarser projections
(`timeStepMs` 4.5 M → 86 M ms), all 200 / ~5.5 KB, and ended at "data unavailable". The old client's
own validation/admission rejects small valid responses, which is why the heatmap and history path is
being rebuilt rather than patched.

## Server

CPU profile of the long-running instance (node inspector, 40 s, original code): **89.6 %** of
samples are under `runRetainedAdmission`; `core/retained-bytes.mjs` `visitParts` alone is 42 % self time,
followed by `immutable-trade-accounting` (8.5 %) and `immutable-session-row-bytes` (~18 %). `/api/diagnostics`
`eventLoopDelayMs`: p50 89 ms, p95 488 ms, p99 930 ms, max 30 s; the process also evicts live state
under its own RSS cap (`diagnostics-cache-rss-pressure`).

After `retainedAllocationBytes` became a constant and the budget coordinator timer stopped
evicting: a private instance is **72.7 % idle** under the same live feeds, event-loop p50 21 ms,
p99 37 ms (the only long stall is the ~7 s startup). What remains is real work: `decimalPlaces`
4.7 %, `usdBookLevels` 4.2 %, depth history recording.

`/api/state` is 1.3 MB of JSON per fetch (oi 519 KB, candles 324 KB, books 91 KB, booksByKey 93 KB,
layers 74 KB, trades 156 KB).

The existing durable heatmap store holds only 294 columns / 18.7 k cells and nothing for Binance, so
there is no multi-day history worth preserving; the replacement recorder starts clean.

## Re-measurement with 24 venues and the Liquidity Tracker on (2026-10-04, later)

The first table above was taken with four venues. Since then the venue picker offers 25 (24 deliver books; BitMEX serves empty ones), the live levels frame grew from ~115 KB to ~510 KB at 4 Hz, and the LT row recomputes in the raster worker. Same method (isolated visible headless Chrome, `INTERACT=1` pan/zoom script, 25 s window, 25 s warm-up), LT row on, private server on `:8788`:

| | 1h timeframe | 4h timeframe |
| --- | --- | --- |
| Venues delivering books | 24 | 24 |
| Frame p50 / p95 | 16.7 ms / 16.8 ms | 16.7 ms / 16.8 ms |
| Frames in the window | 1,585 | 1,608 |
| Raster busy time in the worker (last raster) | 14 ms | 17 ms |
| JS heap | 16 MB | 20 MB |

LT call (worker round trip, 24 venues, `hub.lt`, 5 calls after warm-up): 120 columns (2 h) 7-10 ms; 259 columns (6-24 h of what is recorded) 8-9 ms; the first call after a page load costs 20-29 ms (JIT). Columns are decimated to the view width (`loadColumns` picks the step), so the column count, and with it the cost, stays bounded by roughly the plot width regardless of the span; at ~0.035 ms per column the worst case (~1,300 columns) is about 45 ms, run at most every 1.5 s while the live edge is visible. No optimisation was needed; if it ever is, the two cheap options are skipping bins more than ~20 half-lives from the touch (weight below 1e-6) and recomputing only the live column on the live-tail refresh.

## Server CPU with 24 venues (2026-10-04, later)

The client numbers above hold, but the server had become the limit: with 24 venues and no browser connected a 25 s inspector profile of the private server showed 1.5 % idle, event-loop delay p50 / p95 / p99 of 48 / 237 / 571 ms, and the footprint API timing out or missing Binance executions for many minutes (a starved loop misses pings and drops the trade socket). The profile pointed at four things:

| Cost (share of the main thread) | Cause | Change |
| --- | --- | --- |
| `applyRows` 21 % self, GC 19 % | every delta message rebuilt a Map of the whole 1,000-2,000-level book, re-sorted it and allocated an object per level | merge the few updated levels into the sorted array and reuse untouched level objects (`public-depth-session.mts`; a 3,000-round randomised test checks it against the old implementation) |
| `capSortedBook` 10.5 % | looked up per-level metadata for every level of every message although most venues carry none | return early when the side has no metadata (`http.mts`) |
| `ws` permessage-deflate 16 % | inflating every frame | feed sockets no longer negotiate per-message compression (`live-feeds.mts`); more local bandwidth, less CPU |
| Bitunix / BitMart ~14 % | full depth snapshots re-sent many times a second, each parsed and copied | the connector keeps only the newest frame per 400 ms (`connectors.mts`) |

After the changes the same profile shows 43.5 % idle (about 56 % of one core), event-loop delay p50 / p95 / p99 of 22 / 49 / 75 ms, and Binance executions recorded in every minute again. What remains is the legacy per-message book re-normalisation (`bookFromSnapshot`, `applyBookDelta`, `sortedBook`, `usdBookLevels`, about 20 %); the next step, if more venues or more load are wanted, is to keep a mutable sorted book per venue instead of rebuilding the retained state from the session on every message.

### Second round: saturation bursts

The first round cut the average, but a five-minute profile (not 25 s) showed the loop still saturating whenever the market got busy: mean 81 % busy, 113 of 331 seconds above 97 %, longest unbroken run 34 s. During such a run timers and feed heartbeats starve, which is what showed up as multi-second to minute-long "stalls" in `/api/diagnostics` (max 74 s) and as feeds dropping on heartbeat timeouts. It was not a hang: the profile had samples throughout, dominated by the legacy reducer (`bookFromSnapshot` `side` 11.6 %, `applyBookDelta` 7.8 %, `sortedBook` 3.7 %): on every message the retained book was rebuilt as objects, then as Maps, the Maps were copied and everything was re-sorted. Snapshots made of plain, strictly sorted price/amount rows (what every depth session emits) and deltas on books without level metadata now take merge-based fast paths in `src/core/normalize.mts` (`sortedBookFromSortedSnapshot`, `applySortedDelta`), with the original code as the fallback for anything else (metadata, unsorted or invalid rows). `tests/normalize-fast-paths.test.mts` checks 7,000 random cases against the original functions.

| 5.5-minute profile, 24 venues, no browser | Before | After |
| --- | --- | --- |
| Mean main-thread busy | 81 % | 60 % |
| Seconds above 97 % busy | 113 of 331 | 14 of 331 |
| Longest unbroken saturated run | 34 s | 2 s |
| Event-loop delay p95 / p99 (steady state) | 82-95 ms / 414-522 ms | 60 ms / 130 ms |

The long `max` values in `/api/diagnostics` are a high-water mark since start (startup alone reaches ~6-10 s while 24 venues snapshot and the venue selection restores), so judge the server by p95/p99 and by whether `max` keeps growing.

### Third round: what a "level" costs

An 18-minute profile with a one-second poller on `/api/health` (the loop answers late when it is blocked) still showed runs of 5-82 s during market bursts, and the stall windows were now dominated by the fast path itself: `merge` in `applySortedDelta` at 37 % of those seconds. The profile's per-line ticks pinned it to a single comparison inside the two-pointer merge. A warm micro-benchmark had hidden this: each level is a separate heap object, so walking 1,500 of them per message is cache-cold in the server (24 books rotating) and costs ~86 us instead of ~5 us. A cold-cache benchmark (24 rotating 1,500-level books) compared the strategies:

| per batch of k updated levels | linear walk | splice (binary search) | segments + concat |
| --- | --- | --- | --- |
| k = 8 | 86 us | 17 us | 16 us |
| k = 60 | 128 us | 48 us | 74 us |

Both merges now edit a copy of the sorted array by binary search and splice (up to 400 updated levels per side, then the sort-once rebuild). Sides built this way are recorded as strictly best-first (`src/core/sorted-levels.mts`), so the next message skips re-verifying order and the coverage bounds come from the two ends. The same 18-minute soak, same machine, different market hours, before and after:

| 18-minute soak, 24 venues | Linear-walk merge | Splice merge |
| --- | --- | --- |
| Responses slower than 1.5 s | 57 | 4 |
| Worst response | 82.6 s (with dropped requests) | 2.0 s, none dropped |
| Seconds above 97 % busy | 418 | 48 |
| Longest unbroken saturated run | 80 s | 4 s |
| Mean main-thread busy | 83 % | 61 % |
| `merge` share of the profile | 12.9 % | 4.6 % |

What is left on top is `usdBookLevels` (10.5 %, valuing 24 books at 4 Hz) and GC (3.6 %). The market differs between runs, so read these as before/after under comparable busy periods rather than as a controlled experiment; the micro-benchmarks and the randomised equivalence tests are the controlled evidence.

## Known follow-ups

- `src/server/history.mts` still carries the retired heatmap/depth-sample store (unused by the UI; only flushed on close) and `http.mts` is still the largest reducer module. Both are candidates for the next prune now that nothing reads their output.
- The depth recorder starts empty; nothing is back-filled. Footprint likewise only records trades seen while running.
- Provider layers (liquidation, stop loss, take profit) are mock data unless HyperTracker is configured.
