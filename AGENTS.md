# LiquidityMapperFast agent instructions

## Language and checking

All authored application code, scripts and tests are strict TypeScript: `.ts`/`.tsx` (browser, shared) and `.mts` (Node ESM). Keep the three compiler projects strict (`tsconfig.json` browser+shared, `tsconfig.node.json` server, `tsconfig.tools.json` scripts and tests); do not enable `allowJs`/`checkJs`, add blanket `ts-nocheck` or broad `any` casts. Type annotations do not validate exchange frames, HTTP bodies or storage: validate at those boundaries at runtime.

Permanent non-TypeScript exceptions: generated build output (`dist/`, `build/`), the generated WASM glue in `src/app/wasm/`, and the Rust kernels below.

## Rust/WASM compute kernels (approved exception, 2026-10-04)

Compute-bound inner loops (heatmap rasterisation, level grouping) live in `crates/hlm-kernels`, compiled to WebAssembly with wasm-bindgen. Rules:

- Kernels are pure functions over flat typed arrays; JavaScript owns all state, validation and I/O. A kernel holds no state between calls, touches no DOM and parses no exchange frame.
- Every kernel has native `cargo test` unit tests (`npm run test:wasm`) and a Node contract test (`tests/app-client.test.mts`) that loads the committed wasm and checks it against the server's JS implementation of the same spreading.
- Build with `npm run build:wasm` (needs the `wasm32-unknown-unknown` target and `wasm-bindgen-cli` 0.2.129). The generated glue and `.wasm` in `src/app/wasm/` are committed so a checkout builds without a Rust toolchain; regenerate whenever the crate changes.
- The crate keeps its default `crates/hlm-kernels/target/` (gitignored); create no other Cargo target directories.
- Do not add WASM for work that should not run at all. Memoise or delete first; profile before and after and record the numbers in `Research_Findings.md`.

## Scripts (code people write and share)

- A script's text is never given to `eval`, `new Function`, a Blob or a `<script>`: `src/app/script/lang/` interprets it, and that interpreter is what keeps a script from the page. Keep it so: a script sees only values the interpreter made for it (numbers, texts, its own arrays and prototype-less objects, `NativeFunction`s and `HostObject`s with listed members). Every lookup by a name a script wrote goes through `own()` (or a `Map`/`Set`) so an inherited name (`constructor`, `toString`) finds nothing, and `isPlain` accepts only objects without a prototype.
- Everything a script does costs steps (statements, loop turns, calls) and so does what it makes (`charge()`: an array element a step, sixteen characters of text a step); arrays and texts have hard caps. The worker host ends a run that passes its deadline. A new function of the language that makes or grows something must charge for it.
- The language's words (`Math`, `Invalid Date`, function names) are code, not text a person reads: `script/lang/` is skipped by the i18n test, and what a person reads of an error goes through `script/messages.ts` (error codes, never sentences, in `lang/`).
- The reference language for compatibility is described behaviourally in a clean-room note outside the repository (`Research_Results/`); its implementation is GPL and must never be copied here, and nothing in the repository names it.
- A script reads the chart market's own candles of the chart's timeframe, as many as the Scripts panel's **Candles per script** says (`state.scriptBars`, `script/bars.ts`: 2,000, 5,000, 10,000, 20,000, 50,000 or 100,000; 10,000 by default, 2,000 on a phone; the person's own, not a layout's; Karl, 2026-11-10: "at least 10K ... a configuration ... to choose even more"), never another timeframe's. They are read from the exchange (`hub.scriptHistory`, a `KeyLevelHistory` through the venue queue, once the map has its first data) and handed over by `HeatPane.scriptCandles` only once they reach the start or hold all the exchange has, never part by part (each part would be another first candle and every script would run from it again); the chart's own candles take their place where both have one. The start is `scriptStart`, the count back from now on a chunk's boundary (`scriptChunk`: a tenth of the count, at least 1,000), so a script runs from its first candle once a chunk, not at every candle. Where they cannot be read (the chart's market has no history the page can read, the chart shows a reference market's candles, a view all before the start) or while they are being read, a script reads the chart's candles and the price history before them as before (`SCRIPT_WARM_BARS` before the view, at most `PRICE_QUERY_BARS`). Measured on the page 2026-11-10: 10,427 one-hour candles 9.6 s after the chart's own (most of it waiting for the map's first data), the VWAP starter over them in 136 ms; 105,604 one-minute candles in 27 s, the starter in 1.0 s. A run over other candles (a chart opened, more history, a setting) has `FULL_RUN_MS` (10 s), a live update `RUN_MS` (2.5 s), and so does a run from the first candle over the same candles as the run before (a script that keeps an array or writes its options is never put back, so it runs every candle at every update). `sum`, `sma` and the like keep their "fewer while fewer exist" meaning (the starters rely on it), and the run warns instead (`long-window`: the longest window asked of `sum`, `sma`, `cma`, `highest`, `lowest`, `linreg`, `last` or `stoch`, its line, the length asked and the length it has, at most `MAX_WINDOW` (100,000, the most a script can read), and the candles read, as `line|asked|window|candles`; the panel says it against the candles the scripts read: within them, this chart gives fewer; beyond them, choose more, up to 100,000; asked longer than any window can be, it counts back the longest; Karl, 2026-11-10: a user's converted 7D-365D rolling VWAP drew its 90D, 180D and 365D lines as one, and placed in its own row by default it showed two flat lines; `Research_Findings.md`). Where the page recorded no flow, a set's `vbuy`/`vsell` come from the own candles of its Binance markets, spot and perpetual added up (the only candles that say who bought; Karl, 2026-11-10: a user's CVD script drew the perpetual's history and only the recorded part of spot's): `ScriptData.#takerCandles` reads one `hub.scriptHistory(tf, bars, id)` a market (keyed by market, `withBuy`, the four last kept; the chart market's is the same history its candles come from), asked from the scripts' start once the map has its first columns and used only whole (`wholeHistory`); `setSides` never adds up a sum short of a market (a set reads none while one of its Binance markets is being read or failed), and a market before its listing (`KeyLevelHistory.listedFrom`: the first bar the read that said nothing older held, kept when old bars are let go) adds 0. The coin's Binance markets the page reads belong to the sets before any trade of theirs is recorded (`ScriptData.markets`, under the feeds' names only, `takerTarget`: the chart's alias `binance:BTCUSDT:spot` would count spot twice).
- **The functions over a window answer in constant time** (`builtins.ts`, 2026-11-10, `Research_Findings.md`): one window per place in the text (values from an offset, a compensated running sum and a placed sum for `linreg`, monotonic deques for the extremes, `stoch` and the pivots), so a window can be `MAX_WINDOW` (100,000) long. They keep the old answers exactly (`tests/fixtures/builtins-before.mts` is the old code, the oracle of `tests/script-windows.test.mts`): the extremes, `last` and the pivots to the bit, the sums to the rounding. A function's state is plain arrays and numbers only: the engine copies it with `cloneState` for every live update, and a typed array or a class instance there would not survive the copy. A run from the first candle has `FULL_RUN_MS` (10 s), a live update of the newest candles `RUN_MS` (2.5 s); `ScriptHost` gives each script `FULL_RUN_MS` before it ends the worker, so the two move together. The interpreter (about a microsecond a step) is what is left: a 43,000-candle run of the stochastic heat map takes about 6 s.

## Performance and memory

The earlier byte-accounting "admission/lease/grant/reservation" machinery was measured as the dominant CPU cost on both client and server and was removed (`Research_Findings.md`). Do not reintroduce per-message or per-frame memory estimation, cross-tab byte leases or response-size reservations. Bound memory structurally: ring buffers, fixed retention windows (`RETENTION_MS` in the recorders), capped frames.

Measure with an isolated, visible-state headless Chrome over CDP. A tab reporting `visibilityState: hidden` has throttled timers and rAF; its numbers are meaningless. Use the real GPU path for WebGL timings (software GL says nothing about GPU frame time).

- A feed restart must never leave the server without feeds. `LiveFeedManager.start()` retires every old feed before its metadata requests, so an error in between used to leave a running manager with no feed and nothing to reopen one (12 hours of frozen candles and seven stopped venues, 2026-10-06; `Research_Findings.md`). `start()` now schedules a recovery with the last configuration that finished, a watchdog (`checkLiveness`) catches a start that hangs or a manager with specs and no feed, and `/api/diagnostics` reports `feedManager`. Keep new work between retire and open inside that guard, and keep recovery and watchdog timers `unref`ed.
- **The history store (`history.sqlite`) has a hard 224 MiB budget and refuses every write while its file is over it.** `npm run dev` runs HyperTracker in mock mode, and its made-up layers once filled the budget in six days (206 MiB of 224, 2026-10-11): candles and open interest stopped being saved for hours, silently. Mock layers are never written (`recordLayer`), ones an older build wrote are deleted at start with a compaction (`#dropMockLayers`), and a VACUUM is followed by a TRUNCATE checkpoint so the file shrinks at once (in WAL mode it shrinks only when checkpointed). Anything new written there needs a size that stays well inside the budget.
- **Stop serving before closing a store.** `server.close()` keeps a connection that is still busy (a large response draining, a body being read), and the page sends its next request on it once that ends; at a restart those requests reached the closed history ("statement has been finalized" on /api/v2/oi). Shutdown and a failed start call `app.stopServing()` (close, then `closeAllConnections`) before `v2.close()` and the history store, and a failed start closes v2 so the process exits (`tests/startup-process.test.mts`).
- **Zoomed out over days** (`Research_Findings.md`). The server merges minute columns into wider windows in flat arrays (`mergeWindow` in `shared/recorder.ts`, equal to the old map merge to the last bit; keep the test) and keeps windows that have ended; the page asks for column steps that double (`hub.loadColumns`) so zooming reuses them, and its 30 s refresh asks only for the windows that could still change (from `settledBefore` of the last answer; the worker splices them in with `withTail`): never ask a source for a whole window again on a clock. The columns are held per instrument and per step (`ColumnHolds` in `app/column-holds.ts` is the page's record, `RecordedColumns` in `worker/column-store.ts` the worker's, kept in step by the `columns`, `columnsTail`, `columnsUse` and `columnsDrop` messages): a book that comes or goes asks for itself only (the worker reads the books a pane names, so a dropped book keeps its columns until its window is an hour old), a zoom back to one of the last `COLUMN_STEPS_HELD` steps asks for nothing, and a book or step left unrefreshed is brought up from its own `settled`. Do not merge held fine columns into a wider step on the page: the server's `finish` cuts the small bins after each merge and the trackers need `ltN`, so the result would not equal the server's merge. A merge on the request path blocks every other request: measure one before adding it. Anything a pane asks the worker for is keyed by what changes its answer, never by the view to the millisecond (a map following the live edge moves every frame): the depth pane counts whole columns (`depthKey`) and refreshes what is live on a clock, the raster is redone for the live edge no more often than eight times its own duration (new columns, a pan or a zoom at once). A frame that only moves the pointer must not judge or regroup data: absorption keeps its judged marks until the groups or thresholds change and its squares until the map moves a pixel. It does not draw the map either: the legend, the Range box, the book's row and the crosshair with its box are the pointer's layer (`heat-pane.ts` `#hoverCanvas`, `#renderHover`), and the overlay is drawn again only where what it draws of the pointer changed (`#hoverKey`: the strip's bar, the bubbles' venue, the top bands' bucket, the columns' mirrors); a new paint that reads the pointer goes on that layer or into that key. The flow column draws another pane's pointer line on a canvas of its own the same way. No blurred shadow drawn per item per frame (the whale glow is a cached image, `glowOf`).
- **Older history from disk** (`Research_Findings.md`). The server holds `HOT_MS` (24 h) of depth columns and footprint rows in memory (a footprint minute's sums and statistics for the week) and reads older ones back from SQLite by the hour when a question reaches them (`ColumnStore.range` / `extent`, `FootprintStore.range`); a recorder whose store cannot read back (the browser) keeps its whole retention. A column or minute leaves memory only once the store has it, a late trade or order for a minute only the store holds reads it back into memory first (`#rowsToChange`), and an hour read back is kept only when it can no longer change and goes at the retention cutoff. Whatever a recorder keeps for the next question goes in a `KeptCache` (`shared/kept-cache.ts`): it never lets go an entry asked within 45 s and makes room in one go. Letting the least recently asked go one at a time kept nothing of a view wider than the cache (the page asks its whole window every 30 s, so each window went just before it was asked again) and cost 20 µs a window, since a `Map` walked from its oldest entry steps over every entry deleted since. Measure the first look after a start and the refresh separately, with a clock that moves.
- **The page paces its reads** (`Research_Findings.md`, 2026-11-07). The page builds its hub with `{ paced: true }` (`main.ts`); a hub built for a test asks at once. Paced: a column step or a wider window is asked for once the zoom has rested 200 ms (`COLUMN_STEP_SETTLE_MS`; a wheel turn asked for every step it passed, tens of MB each at days), one column load out at a time, finished rather than let go for a newer step (letting it go measured no better: each step then started a question of its own, and the server stops an abandoned one only after the instrument it is on); on the server's page the history the first frame does not need (open interest, profiles and value areas, bubbles, liquidations, absorption, flow minutes, the flow strip's sizes and price, the depth sound's hours) waits for the map's first columns or 10 s (`Hub.mapFirst`, `MAP_FIRST_MS`): the books are known only from the first live frame, and asked behind some twenty other reads the columns came 18-36 s after the page opened on a busy PC, 4.5 s since. A new history read on the server's page that the map does not need for its first frame checks `hub.mapFirst()`. Bubbles and liquidations are not asked while the stream opens for the first time (that answer covered nothing). Scripts load liquidation days and flow only when they read them (`analysis.ts`: `lbuy`/`lsell`, `vbuy`/`vsell`/`recorded`, by name or through `bar`; `bar` handed on whole is marked `bar` and loads both). A phone's covered map (`hub.mapCovered`) makes nothing wait.
- **WebGL programs are built beside the page** (`src/app/gl-build.ts`, `Research_Findings.md` 2026-11-07). Start a program with `startProgram` and draw only once `built` says it is (asked without waiting, with KHR_parallel_shader_compile switched on again for every program, since a context given back is the same object); never ask a program's link status or uniforms right after linking it, which waits for the card behind the first frame's drawing: the glass's four programs held the first second ~200 ms, the dust's three ~100 ms and the phone Tape's five ~0.6 s. Until its programs are built a renderer draws as without WebGL (the page stays solid until the glass is built, the Tape draws its solid panel). A second WebGL context made inside the first frames waited 320 ms for the GPU process (the dust's, now made in an idle callback). A canvas that redraws often and changes rarely paints its still part on a canvas of its own and copies it (`cvd-strip.ts` `#paintStill`: the flow column's ~700 dots were a fill each, 60 times a second).

Script that must differ reads `isPhone()` / `compactBar()` / `isCoarse()` from the same module.
- A phone must not write the desktop's saved layout (`hlm-layout-v2`): `Layout.#persist` returns early when `isPhone()`. The dock's own sizes use `hlm-dock-size`.
- **First-visit defaults** (Karl, 2026-10-17). No pane under the map is on (`DEFAULT_SHOW` in `store.ts`: Depth, Open interest, Delta, L/S, LT and the Footprint's bar stats are each one switch away); the flow column and the book are. And on a touch screen in the phone arrangement (`initialState(phone, touch)`: `isPhone() && isCoarse()`, never a desktop window that is merely narrow) a save from before it has the Flow and LT panes on once (the tab bar hides a tab whose pane is off, and a Flow saved off was never found again); a desktop keeps the panes it chose. - Never let a floating panel, menu or dropdown rely on `position` computed from its anchor on a touch screen: they are bottom sheets there (`ui.ts`, `menu.ts`, `sheet.ts`).
- **The Tape tab** (`panes/candle-pane.ts`; `candle/model.ts`, pure and tested; `candle/trail-gl.ts`; its id stays `candle` in the dock and `hlm-candle-v1` in storage) is a phone tab that fills the area in place of the map, and the tab a phone opens on (`defaultTab` in `dock.ts`, applied while no tab was ever tapped and judged by the layout the window is in NOW, so a browser's phone view opened from a desktop-sized window gets the Tape too; the key `hlm-dock-tab-v3` is new with that choice, so a phone that kept the Map opens on the Tape once). Nothing is fetched and nothing restarts it: no timeframe, no recovery, no bar that resets (Karl, 2026-10-17: a one-minute candle that keeps resetting kills the flow, and the tab must open at once). The header is one slim row, the readout and help: since when, how many markets, and the minutes missed while the page was hidden (a background phone gets no trades; gaps over 5 s count); its choices (Look, Trail, Glass, Rows, Pulses) are a Tape section of the phone's Settings (`settingsFields`, hosted by `toolbar.tapeFields`), never in the header. The live book is either side as one silhouette per side (one faint fill under a crisp outline: venue pieces read as two tones of one book, Karl 2026-10-16), with an arrival rail and the trade trail behind it: every order of the window at its exchange time and price. Settings live in `hlm-candle-v1`, never in the page's saved state or layouts. Flashes on the rail are timed by arrival, the trail by exchange time. Buys are filled and sells hollow in every look, so the side reads without colour. Exchange marks go only on orders from the Bar stats' whale size up and on the largest flashes. Glass (`glass`: off, panes, bricks) is three pieces welded together over the trail, the bid book, the tape and the ask book (bricks: glass only inside each row's bar), drawn in WebGL from an off-screen copy of the trail blurred at a quarter of its size, never with `backdrop-filter`. Rows show their winning side more strongly the more it won (`rows`: glow, lean, delta; `rowEmphasis`), and resting liquidity added or pulled pulses its row (`pulse`: pressure, deposit; `PulseTracker` holds Astra's rules: a change counts only past the side's noise and on two frames, a row a trade reached is marked traded, a removal the price passed with no trade there is not called a pull, and a gap of more than two windows starts it afresh); a stack sends a shock out along the bar and a pull one back in. Orders of $25K and up (coin-scaled) send a wave from the rail through the glass (`glass/waves.ts`, the page's glass's wave field, an instance of its own): the panes are glass to it and the welds walls. `?rows=`, `?pulse=`, `?glass=` and `?style=` set and keep a look from the address. The source is gated afterwards (`gatedCarries`): from the recording only a kind it can hold two windows of at all (`recordedCount` at least 2: a server carries yesterday's and never a previous week, a page that keeps a day carries none, and the panel says so in a note instead of leaving the switch looking live) and a source that began inside the retention (`recordedWindows`); then an answer for the whole window held for `DRAWN_SHARE` of it (`recordedWindowLevels`, the one rule `#windowLevels` reads) or the candles reaching it. A source that fails is no carry, **the window before it is never put in its place**, and it is asked for on its own whatever `count` is (`#ensureValueAreas`). Candles reach back and months always come from them. The carry follows the source's own cohort, revisions included: late trades revise a recorded answer for an hour after the window ended (`VALUE_AREA_SETTLE_MS`), a recovery drops it (the carry waits for the new answer), the spot market's candles join the perpetual's once they reach the window. The carry replaces the source's own untouched run over the window under way (the same level, from where its window ended): the run is hidden over that window alone (`runPieces`), so no level is drawn twice while the gap before a session that began later and what is left of the run past the window's end keep their dots; older windows' runs stay as they are, and a carry reads no touch evidence at all (the same touched or not). The cost, chosen with Karl's words ("dashed and subdued, whether or not they were touched"): the newest previous POC no longer shows whether it was touched, though older ones still do. Names and tags rank the current window's first, then the carried (labels 0.5 and 1.5, tags 5 and 6), then older windows' (labels +2, an older run's tag 8). **Age fading** (`ageAlpha`, `ageRanks`, `#ageRanks` once a minute): by the calendar up to now (the same whatever the chart shows: panning back does not make an old day new, and a window not drawn for lack of coverage still ages), the two newest windows of each series are drawn in full, then a tenth less for each one further back down to 0.6, for the lines and the profile bars; the backing under a profile's bars is never faded and names keep at least 0.85, so a faded window is still read. Sol 6.1's review of the design (2026-10-25) also found, and this change fixed in the code beside it: a replay's naked-run touch read the candle still forming (its high and low are from after the moment: `touchedAt`'s `closed`), the touch cache key lacked the window's end and the candle under way's range, and `candleLevels` made millions of rows a bar when the grid step was still a billionth (no price known yet): now a bar over `MAX_BAR_ROWS` (100,000) or a window over `MAX_WINDOW_ROWS` (4 million) is refused, so that window has no lines, profile or carry, and says nothing about it. Not done: a naked run judged on candles that stopped refreshing still claims "untouched" up to the right edge (no known-through horizon); the `count × day + 3 days` lookback of `#linesWindows` cannot supply 20 weekday sessions.
- **Where each profile is drawn** (Karl, 2026-10-20: "completely personalise the location: top, right side or left side ... not just for open interest but absorption, liquidations and possibly more"). `traded.placements` (`app/traded/profiles.ts`) is a versioned list of profile instances: an id given once (`metric:placement`), the measure, the place (`right`, `left`, `top`), its order (outward from the plot; the registry's), and a window, a size and a look of its own that version 1 always reads back as the chart, null and none (one instance a measure and place). `readTraded` reads an older save's `metrics` (or one `metric`) as columns on the right and its `top` (or a `measureStrip` beside it) as the band it was, off where it was off; reading is idempotent (tested, layouts too); a switch turned off keeps its instance. The panel's grid (`traded/placement-panel.ts`, rows from the registry, a cell a place) and its small picture of the chart replace the old Columns switches and the Time profile switch and select; the band's header opens that section (`data-section="placement"`). **Measures are registrations** (`app/measures/defs/*.ts`, listed in `measures/registry.ts`, the shape in `measures/measure.ts`): names, side words, header, notes, completeness, whether it is judged at the absorption marks' thresholds, and its by-price (`instruments`, `keyOf`, `ask`, which the hub's `ensureMetricProfile` and `ensureTraded` call) and by-time (`worker`, kept per measure by `TopBands`) providers. A new measure is one file there plus its line in the registry, and shows in every place. `measures/model.ts` must not import the registry as a value (the measures' files import model.ts; a cycle there left a registration undefined when a measure's file loaded first). Questions are keyed by measure and projection, never by place: `priceQuestions` asks each drawn measure once, `hub.ensureProfile`/`hub.profile` read one answer for both sides. **Left columns** sit inside the map's pane between the flow column and the plot: the overlay, the pulse layer and the panes under the map draw in the plot's coordinates (`ctx.translate(left, 0)`, `leftGutter`; the left columns at negative x), the heatmap and dust canvases are moved by `left`, pointers subtract it (`bindTouch`'s `originX` for fingers), and `--gutter-left` moves the replay bar. A left column is the mirror of a right one (bars from the map's edge outward, tags at the outer edge, box opening over the map; `columnHit` is the mirrored hit test). **Room** (`traded/arrange.ts`): `COLUMNS_FIT` counts both sides (taken in turns, nearest first, the right side first on a tie); up to three bands stack (`stackedBands`: 96/70/56, a quarter of the plot at most, none under 32 px), the first by order lowest; what has no room stays on and is said (the panel's note, an amber tag on the map that opens the panel). Phones: no columns, one band. The lines across the chart are traded volume's wherever it is drawn by price, else the first measure drawn by price (`lineMetric`), never following the room, and the panel names the measure.
- **The columns' measures** (`measures/defs/`, `hub.ensureProfile`, `sideColumns` and `priceQuestions` in `heat-pane.ts`). Each column is `TRADED_W` wide; the map keeps half its pane (`COLUMNS_FIT`, both sides together), so a narrow one draws only the nearest that fit (`gutter` and `leftGutter` count them). Each adds up, over the same window (what is on the chart: the columns always follow it, `#tradedWindow`), its own `ProfileAnswer` whose two sides take the bid then ask places, so the bars, POC, value area and hover read them unchanged; the hub asks and keeps each measure apart (`MetricColumn`). The lines on the chart are traded volume's when it is drawn by price on either side, else the first measure drawn by price, and a non-volume one draws only its own levels over that window (past days, weeks and sessions stay traded volume's, and the panel says so). Absorption: `markedPart` of each group at the threshold the Absorption settings judge it at, counted once (the marks' minutes are loaded for it even with the marks off). Liquidations: the source's record (its largest 5,000 when more match: the header says "the largest 5,000"). Open interest (`shared/oi-profile.ts`, `/api/v2/oi-profile`, the engine's `oiProfile`): each perpetual's change between consecutive one-minute bars, put in the minutes after the first reading up to the end of the second, spread over the prices that traded on that market in them by their share of the USD (`FootprintRecorder.spread`), linear markets in coins valued at each row's price, inverse ones (`inverseOiId`) in their own USD; increases and decreases apart, each venue on its own. A change across readings over `OI_GAP_MS` (an hour) apart, past the window's edges, or over minutes with no trades recorded is `unplaced` (signed USD), never spread elsewhere; the header says it when over a hundredth of what was placed. It is an estimate of where exposure grew or shrank, never of who or of entry prices: never call it new longs. A header sub-line in amber is a cut or incomplete record.
- **Order counts by price.** The footprint recorder counts each market order in the row of the price it started at (a buy's lowest fill, a sell's highest) in minutes begun since counting began; such a minute is stored as five numbers a row, an older one stays uncounted (three numbers), and an order never makes a row without volume (`nearestCell`). Keep `profile` and `query` answering three numbers a row: open pages parse those strictly.
- **Order sizes as settings.** Every size a person sets (retail and whales in the Bar stats and the dot rows, the smallest bubble and liquidation, the Liquidity Tracker's Min and Max) is any value, typed or picked from a menu (`sizeRow` / `sizeControl` in `ui.ts`, `takeSize` and `parseSize` in `sizes.ts`), saved as BTC's dollars and scaled for the coin. The recording keeps each minute's market orders from $25K one by one beside the size boxes (`TradeStats.big`, signed USD, the stored stats' optional sixth element), so a line can be drawn at any size from there: the footprint and sizes questions take up to four `cuts` and answer `over` only when every minute they count has its list. Minutes recorded before the lists are filled in from the prints after startup, in memory only. A page asks only for lines between box edges (`linesToAsk`: at an edge the boxes are exact, so the defaults send the requests they always did); where `over` is missing (an older server, minutes not filled in yet) it takes the nearest box edge and marks the row "≈". A saved box number from before reads as its edge. The whale VWAP's four sizes are the in-memory bands of `shared/print-sums.ts`, not lines.
- **Liquidations.** Only Binance (`forceOrder`, its own socket in `Made.liquidations`, at most one per symbol a second: `throttled`), Bybit (`allLiquidation`), OKX (`liquidation-orders`, every swap on one channel, filtered by instId) and Deribit (the `liquidation` flag on its trades) publish them; Hyperliquid, Coinbase and every spot market publish none, and `LIQUIDATION_COVERAGE` in `shared/liquidations.ts` is the one table of that. The side is the position closed (`long` = the exchange sold), read per venue (Binance's order side is the opposite of Bybit's position side; Deribit's M/T flag says whether the maker or the taker was forced). Bybit reports the bankruptcy price (about 0.3 % past the mark on BTC), which the market need not have traded at, so a `bankruptcy` report is drawn at the instrument's last trade if that came within a minute of the liquidation's own time (a report can arrive minutes late: then at its own price, and the box says so), and the box gives both prices. OKX calls its price `bkPx`, but it was measured within a few basis points of the mark, so it is a `fill` like Binance's and Deribit's, drawn where it went. For this the last-trade maps (`lastPrice` in `api.mts`, the engine's `#last`) keep each trade's own time. The server records them from $100 for a week (`liquidations` table, `/api/v2/liquidations`, pushed as `liquidations` on the socket) even for a venue whose book a browser reads, so FlowSources runs a covered venue's liquidation feed alone; the browser engine keeps them in memory only and the panel says so. What a venue does not report is said in the panel (`coverageLines`), never on the chart. A liquidation is also one of the market orders, so the Range line gives its share of all the market volume in the selection's minutes (not of a box's band: it is drawn at one price but traded wherever the book took it) and never adds it; it counts only those from the panel's smallest, and a fill that closed a long and a short (Deribit's MT) once in the share. A selection's panel reads what the map holds again (`refreshHeld`, no new recording question) when the large orders or liquidations arrive or their settings change. Diamonds in the sell colour for longs closed and the buy colour for shorts, as everything else on the page: the shape and its hard edge say forced.
- **Live trades (the trade dust)** (`shared/tape.ts`, `app/tape/`: `ring.ts`, `gl.ts`, `trace.ts`; `Research_Findings.md`). Every market order, as the recorders rebuild it from fills (`OrderBuilder.drain`, the same orders the bubbles are, so a venue that reports every fill does not look busier than one that reports one row per taker), is pushed as it completes in a binary `tape` frame (`encodeTape`, columns plus `seq` and `dropped`) once a pass (250 ms) to a page that asked for it with `{t:'tape',on}` on the socket (an older page never asks and is never sent one, since it reads every binary frame as levels), never skipped for a backlog (`sendVerdict` in `server/v2/backpressure.mts`: it was skipped from 2 MB queued while the 430 KB levels frames, 1.5 MB/s, kept coming to 4 MB, so a stall of a few seconds cost 19 batches of about 1 KB and left holes in the dust, probe 2026-10-19; now only the levels are skipped, from 4 MB, and a client more than 16 MB behind is dropped and reconnects); the browser engine posts the same batches (`onTape`, transferred). Nothing of it is stored anywhere: the page keeps a ring of 2^21 orders (2^19 on a phone; 6 floats each, times and prices relative to bases so a float32 holds them, `TapeRing`) and a reload starts empty; an order timed more than six hours from the page's clock is left out (`CLOCK_REACH_MS`: a bad stamp would rewrite the ring on every batch). A batch that is missing (`seq`), trimmed (`dropped`, more than `TAPE_BATCH_MAX` in a pass, the largest kept) or on a new connection starts a new segment, and the map draws where the live trades begin and each gap the price line breaks at (`gapMarks` in `tape/trace.ts`: a stretch no segment covers (their ranges merged, since exchange stamps overlap) of at least ten seconds and three columns, one column past the line's own break, so a mark is always a break and a break can go unmarked; a skipped 250 ms pass of a page that is behind starts a segment too, but no one can see that hole, and a full-height dotted line for each buried the map in them, Karl 2026-10-19). The dust is its own WebGL2 canvas between the heatmap and the overlay: each order a point sprite (log-scaled 0.75 to 2.2 CSS px for the coin's $100 to $250K, with a hairline over the prices an order walked, at most 48 device px either side: a sprite is never larger than 97 px, since one as tall as a long walk at a deep zoom costs the card a quarter of a million pixels an order) added into a float picture of buy and sell USD per pixel, shown in one pass (colour of the side that traded more, opacity by the log of the volume against the coin's fixed sizes, never the largest in view). Only orders in a block of the ring whose times reach the view are drawn (`runs`). The float picture is wider than the screen and shown shifted by whole pixels, so following the live edge only adds new orders (about 1 ms on an RTX 4070 with 2M orders held); it is redrawn whole on a zoom (2 to 13 ms). Arrivals redraw the dust canvas alone (`tapeArrived`), never the overlay; the arrival accent is the only animation, about 30 frames a second while one fades, none hidden or with reduced motion, and the dust is off in replay. While it shows, candles are hollow (outline and thin wick) and the chart market's price line (`TraceIndex`: each pixel column's first, extremes and last order by exchange time, breaking after ten seconds without one) runs over them, dashed from its prices a second (`FlowSeries.ownPrice`, never carried forward) before the page held orders; Venue lines adds every other market's, faint. The switch is the Trades panel's Live trades row (`BubbleSettings.live`, on by default, inside `show.bubbles`). The server's `state.trades` list is capped at 5,000 rows a pass: a burst beyond that is lost to the dust as it is to the flow and the footprint.
- **Key levels.** The previous day's, week's and month's high, low and middle, each period's open and the high and low so far of the one under way, as lines (`src/app/keylevels/`, off by default; the button is "Key levels" because the order book already has a Levels view). They are worked out from one market's candles read straight from the exchange (`fetchCandles` and `webGet` in `shared/history.ts`, the same in server and browser mode): the server's candle route serves only its own recorded minutes, capped at 400 bars. The candles are hourly, or half- or quarter-hourly in a zone whose clock is that far off the hour (`barMsFor`: India, Nepal, Lord Howe's summer), so every period starts on a bar and none is split. The market is the chart's own where its history can be read (the same instrument: OKX spot under `okx` is not the OKX swap), else the first of a fixed list that lists the coin, and the panel names it (`historyTarget`; a server names Binance spot `binance:BTCUSDT:spot`). `KeyLevelHistory` holds one stretch of bars, reaching back at most `MAX_BACK_MS` (62 days, so the previous month is always held; up to 24 pages a request, which OKX's 100-bar pages need), extends it back only when the chart needs earlier periods, in turns of at most 24 pages while each turn gets older bars, and stops once the exchange has nothing older, asks again for the newest bars every five minutes (`heldTo` is where the last such answer reached), drops bars older than the levels can reach, and waits a minute after a failure; nothing is asked or worked out per frame (the pane keys its caches by the view's hour and the clock's minute). A period's open is drawn when the history held reaches back to its start, and its high, low and middle only when it also reaches its end (`heldTo`, or the chart's own candles running on to now): a missing bar inside it is an interval nobody traded (Coinbase sends none), not a hole, but history that stopped at noon is not a day. After the last bar the chart's own candles (same market, no coarser than the bars) move the period under way. Days and weeks start in the Volume profile's zone (`traded.zone`, shared on purpose so the two never disagree), weeks on Monday, months on the 1st (`monthWindows`). A period's level is drawn only when its candles are complete; a previous level the next period never traded through runs on, dotted, until reached, and once its own period has ended its label carries that period's date and its axis tag is outlined and gives way to the current ones. Tags are placed (`placeTags`) clear of each other and of the live price's tag, never moved off their price, and a grid price under a tag is left out. The colour is the palette's `level` (every theme; the contrast test covers it). The names at the lines' right ends (the Volume profile's, the key levels' and the VWAP's) share one `LabelBoard` a frame (`labels.ts`, tested), claimed in paint order: the Volume profile's first (its lines have no tag on the axis to fall back on), then the key levels', then the VWAP's; a new feature that names its lines takes the board rather than keeping a list of its own (a point of control and a previous low at one price were printed over each other, 2026-10-18). The levels' arithmetic was checked against the exchange's own daily, weekly and monthly candles in UTC (Binance USD-M BTCUSDT, 2026-10-18): every high, low and open equal.
- **VWAP.** The session VWAP (restarting each day, week or month in the shared zone, with optional ±1σ/±2σ bands) and up to six anchored VWAPs a coin (`vwap/`, off by default; the anchors are `anchors/`'s, below) are each bar's typical price (high + low + close) / 3 weighted by its volume in coins (every venue's candle volume is in coins; checked for Deribit's inverse perpetual too), from the same market and the same loader as the key levels (`historyTarget`, `KeyLevelHistory` with a one-minute refresh) or, with the panel's **Candles from: Chosen markets** (Karl, 2026-11-10; `vwap.source`, `vwap.picks`, `vwap/markets.ts`), from up to six markets ticked as exchange and kind (each exchange's spot and perpetual apart, the form `market-choice.ts` saves, so a layout made on BTC means the same exchanges on ETH; switched to, the boxes start from the market the lines read). Several markets are added up bar by bar as `VwapBar`s (`mergeVwapBars`: volume, the volume-weighted typical price and the spread of the markets' prices around it, so the bands keep the distance between markets; Sol 6.1, 2026-11-10), only over bars every market has closed, the lines carried on at their last value to when the markets were last read; every market must reach a line's start (`knownFrom`), and the panel names one that could not be read, has not been read for minutes, or does not reach (with the date), and says when the chosen markets mix USD, USDT and USDC (added one to one). One history per kind, market and bar size (`hub.vwapHistory(id, bar, rolling)`; those in use are never let go). The bar size follows how far back the line reaches (`vwapBarMs`: a minute for a day, five for a week, half an hour beyond) and is never coarser than `barMsFor`, so a session never splits a bar. After the last bar the chart's own candles replace the partial one (same market, no coarser), so no volume counts twice. A session or anchor whose start the history does not reach yet is not drawn rather than drawn wrong; the line begins at the first bar with volume. **Anchors** (a user and Karl, 2026-11-11: "enter a date instead of clicking", "nobody wants to click the exact candle", yearly and monthly highs and lows; designed with Sol 6.1 and the advisor, reviewed by Sol and a Sonnet code review) are `Anchor` objects (`anchors/anchors.ts`: `id`, fixed `at` or a live `rule`, a colour `slot` given when made, an own `color`, `hidden`; a save of bare times is read as fixed anchors), reaching ten years (`ANCHOR_REACH_MS`). A rule is a period (day to year, in the Volume profile's zone) and a point (start, high or low so far, previous high or low): 25, the panels' grid of boxes (`anchors/controls.ts` `ruleGrid`, laid out as the Key levels' grid). It resolves on the chart market's bars of `searchBarMs` (15 minutes for a day or week, the zone's bar beyond), then on that market's minutes inside the winning bar (`Hub.spanRead`, short spans cached; a live one keeps its last rows while the next minute's read is out, or the anchor would vanish each minute), in `HeatPane.#resolveRule` (memo read before any zone arithmetic: it runs dozens of times a frame). A previous period's search stops at its end (its next period's first candle was once taken). Until the minute is known the anchor is not drawn (`coming`), never the coarse bar's start passed off as exact; no minutes there at all gives the bar's start marked `approx` (≈); a history that failed, or that its exchange cuts short of the period (Hyperliquid's newest 5,000 bars, `limited`), says so (`failed`, `short`) instead of "finding it" for ever. An anchored line is a coarse body by the anchor's age plus a fine head for the stretch to its first whole body bar (`anchorBars`; `#vwapLines`); where no head candles come back the line starts at the body and the panel says "drawn from …" (`anchorDrawnFrom`). Placing on the chart (`vwapAnchoring`, `anchorMove` for a Move, `anchorPreview` for a tap or the arrow keys, none saved) places on pointerup at the candle's start (`candleStartAt`): a drag pans and keeps it armed, a click in the future or too far back keeps it armed and says why (`anchorSpot`), a taken candle says so, Esc (a capturing listener, so the panel stays open) cancels, arrows and Enter place, a touch tap previews with Place here / Cancel; whatever commits an anchor another way ends placing. The Range tool and the two anchor placings take the next press, so arming one ends the others. Tags go into the key levels' one tag placement (`KeyTag.color`), the session's ranked with the previous day's levels; a live anchor is named by its rule's code (AVWAP PWH, as the key levels' codes), a fixed one by its date (AVWAP Nov 9 06:00). **Colours** (`vwap.colors` for the session and each rolling window, an anchor's `color` on it; `vwap/colours.ts`): the session the palette's `vwap`, the rolling windows greens and the anchors violets by slot (hues the heat map never draws; lighter on dark themes), each window and anchor slot with a dash of its own (`dashOf`). An anchor's colour is read at paint time by its id (`paintVwap`'s `anchors`): the plan and lines are kept by keys that leave colours out, so a colour dragged repaints at once. Layouts carry colours, never anchors. The panel: rows with swatch, name, start (read again every two seconds), eye, Edit (freeze at the time shown, move to a date or a candle, Undo) and remove (Undo, guarded against changes since), the grid, a date and optional time on the chart's clock (`fromWallFields`: a date that does not exist or a time a clock change skips is refused), Click a candle, jump links to its sections; a refresh from the page waits while one of its fields is being worked (`Toolbar.refreshOpenPanel`), and typed dates survive a rebuild. The whale VWAP (buys in the bid colour, sells in the ask colour, no axis tags) is Σusd / Σcoins of the recorded large market orders (the prints: orders rebuilt from fills, the same as the bubbles) from a size band up, on the flow column's instruments, since the session began or the recording did (the panel says which). Its sums are kept in memory per instrument, minute and disjoint size band (`shared/print-sums.ts`: $100K, $250K, $1M, $5M, BTC's, scaled with the coin), fed by `PrintStream.ingest` after its deduplication and built once from the store when the stream starts (`PrintStore.each`: about two seconds for a week of BTC from $100K, before the server listens). Asking SQLite for the sums per request took 90 to 400 ms for a day and 1.7 s for a week at $25K (measured on the live recording 2026-10-09); do not add a size index to the live prints table instead: building it locks a 600 MB database for seconds, and it helped only from $1M. `/api/v2/print-sums` takes a band edge as `min` (400 otherwise); the page asks again every 45 s for whole minutes and adds the orders pushed since to the minutes after them (`hub.whale`), so none counts twice. **Rolling VWAPs** (Karl, 2026-11-10; `state.vwap.rolling`, windows of `ROLLING_DAYS`, 1, 7, 30, 90, 180 and 365 days, none by default; the panel's rows and its Add buttons, an Add switching the VWAP on as placing an anchor does) are the same typical price by volume over the bars that start in the window before each bar's end (`rollingSeries`: by time, so a missing bar is time nobody traded, never one bar fewer). A window's bar size comes from the window alone (`rollingBarMs`: 5m, 15m, 1h, 1h, 4h, 4h, measured against finer bars, `Research_Findings.md`), so the line is the same at every timeframe and zoom, and the chart's own candles are never put after the bars (the window's start moves by its bars): the newest bar is the exchange's, read again each minute and drawn at the time it was read (`heldTo`). They read histories of their own (`hub.vwapHistory(id, bar, true)`, `ROLLING_MAX_BARS` bars back), since the session's two months do not hold a year. A point is drawn only where its whole window is held: a line starts a window after the history does, or not at all, and the panel says when the history it could read is shorter than a window or could not be read (`rollingReach`, told to the panel only when that changes). Their points stand at bar ends, so a replay keeps those up to the moment (`cutForReplay`); a thin market with no bar under way still gets its window's point at `heldTo`, the window's start moved on. A history is asked for a whole window before the view counted from the view's hour (`rollingFrom`, the plan being kept for the hour), never further back than it keeps, and a view not framed yet (`{ t0: 0, t1: 0 }` until the first candles or price) reads as a window back from now: taken at its word it read every history whole at each page load. Dashes of their own in greens (each window its colour and dash, a colour of the person's own allowed), named `RVWAP 30D`, ranked after the day's key levels and before earlier periods' (there can be six). Every VWAP line is drawn with at most four points a pixel column (`paintVwap`'s path: where the column is entered, its lowest and highest, where it is left), and an axis tag wider than the axis is drawn condensed (`paintKeyTags`' `maxWidth`) rather than cut. **The shared loader** (`shared/history.ts` `readCandles`, `KeyLevelHistory`; Sol 6.1's design rounds, 2026-11-10, checked against every venue): a venue's page throws on an error sent with HTTP 200 (Bybit's `retCode`, OKX's and Bitget's `code`, a JSON-RPC `error`, a non-list answer), never reading as no candles; a read says how far back its pages answered (`coveredFrom`) and why it stopped: Coinbase, Deribit and Hyperliquid answer for a window of bars, so a window with none is time nobody traded and the read walks on; a page short of its limit on the others is the start of the venue's history (`exhausted`); Bitget keeps about a month of minutes and Hyperliquid its newest 5,000 bars, which are limits (`limited`), not starts. The history keeps what its reads covered (`knownFrom`): `reach` and the lines read it, a failed walk is tried again a minute later. - **Liquidity Tracker** (`app/lt.ts`, `shared/lt-sample.ts`). Each venue is measured from its own best bid and best ask and the venues add up; never from one touch shared by all venues (they trade up to ~13 bp apart: USDT spot above the perpetuals, USD spot below; measured 2026-10-11, the shared touch was 6.7 points of imbalance off at 10 bp). On a dark theme an addition lightens and a decrease relaxes the cell toward the panel; on a light one an addition deepens it and a decrease relaxes it toward the panel, so the sign is always more material or less, never a colour. It is a statement about DISPLAYED DEPTH, never about orders: no cancel, trade, iceberg or age is claimed (the wire has lo/hi/usd and no ids or ages; iceberg identification from public data is "not usable", `iceberg-refills-2026-10.md`), and the hover says so. A contact ripple (the Tape's ring, orders from $25K, 0.65 s) says an order reached that venue's depth at that price, not that the depth changed; a change that follows has its own light. The hover of a change adds what traded on that venue at that row around the same time (`tradedInRow`: the tape's market orders that reached the row on the side that takes from it, between the change's two snapshots widened by 1 s before and 0.5 s after because the exchange's clock and the page's differ; unknown, never zero, where the tape has a gap or the venue is not on it; a fact about the tape, not an explanation of the change, and the hover says so). **The comparison grid is the merge's own.** The server and the browser engine merge far levels into buckets that widen with the distance from the mid and report a bucket at its farthest member (`shared/merge.ts`), so a $10 add can move a $100k bucket across a ladder row's edge with nothing changed in the native book. Each valued book therefore carries `step` (`ValuedBook.step`, the number `mergeByDistance` was called with: `app/wire.ts`, `server/v2/wire.mts`, `browser/levels-frame.ts`; an older server sends none and the tracker infers `gridStepFor(mid)` and flags it `approx`), and the tracker compares only within 249 steps of that book's mid, where a bucket is at most one step wide and never straddles a bin, so the merged book holds the native USD per bin exactly (`Research_Files/order_book_physics_20261022/merge-bin-invariance.mjs`: 0 bins changed on multiples of the step, 13 to 54 % on a $50 or $25 row grid beyond $500 from the mid, which includes today's auto step); `rowEvents` shares a cell over the rows afterwards (a coarse band spreads uniformly, as `spread_levels` does). Books are compared publication to publication (63.9 % of venue-frames repeat a book, and a repeated frame never confirms), with a cadence per venue (Hyperliquid's 40 bands every 5.4 s are not a gap), only where the book covers a cell in both publications (a bin past the reach is unknown, not zero), never inside a grouped book's touch span, with a first snapshot, a reconnect, a step or `coarse` change or a gap starting that book again with no event. **Light is a budget.** The Tape's gate on venue cells came about 20 changes a second with 25 (p99 88) of 340 cells lit at once (live study, 25 minutes of BTC on 11 books), and the page flashes more than three times a second over any area, so `CueBoard` lets at most 40 cells show light and the lesser of 12,000 px2 and 5 % of the ladder on screen (at least 1,500) of area at full light together (under W3C's 21,800 px2 flash area, with the Tape and the page's waves besides, which the cap does not cover: composed-page flashing is measured on a busy recording, not assumed), the largest first and every venue's largest before any venue's second; the caps count the light that shows (`shareAt`: a cue whose body and crest are both under a tenth of their peak, about half a second in, holds no place and a tenth of its area), so a strong change is not turned down by forty faint ones running out; nothing bypasses the cap however large the change, contacts come after the changes, charged 1.5 times a wash of their strength in every look (they paint the whole cell), the changes waiting for a draw are folded to one a cell as they arrive (the last one decides its sign) and past 512 the busiest venue gives up its faintest first, and a change with no light leaves a signed mark in the gutter beside the bars (3.5 s; the still face, and all reduced motion shows). **Two canvases.** The ladder is drawn on a material canvas (bars, cells, running-total area, what is under the bars) under an ink canvas (words, venue marks, lines, boxes and the pointer; `canvas.ink`, absolute over the material that sets the scroll width): a cue lights the material and the words stay clear above it, and the pane looks as before (18 configurations, three modes, both themes, hover and Mirror, compared pixel by pixel with the single-canvas build: no channel differs by more than 4 of 255). When anything is lit `CueLayer` copies the resting material once, restores the lit cells from the copy and lays the cues again each frame (0.3 ms for 50 cells against 1.4 to 6.7 ms for drawing the book); when nothing is lit nothing is scheduled; a hidden, covered or replaying book lights nothing and takes no backlog of changes (the tracker goes on observing so its history stays whole). `groupLevels`, `coverage`, `cumulative`, `imbalanceByDistance` and `venueCumulative` are memoised per frame and grouping (a frame never changes: callers read what they get and never write it): a pointer move used to regroup the book, 8 to 44 % of its draw. **Heat is an estimate and says so.** `BookCueTracker.heat`: M the net increases still recent (cooling with a 45 s time constant; a decrease takes proportionally from the recent and the old), U the first snapshot's depth, whose history is unknown, A the recent change (20 s); the strip is as long as the recent share and lies along the bottom edge of the venue's part from its outer end inward, where material is added; it is never the age of an order. **No WASM here:** the tracker step costs 0.07 ms for 12 books x 120 bins and JavaScript matched or beat a Rust kernel (it copies across the boundary: `Research_Results/order_book_physics_20261022/study-perf.md`); the harness that measured it, compared pixels and drives the real pane over a synthetic market is `Research_Files/order_book_physics_20261022/ladder-harness/` (git-ignored, like the rest of the research).
