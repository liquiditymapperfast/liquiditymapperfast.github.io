# LiquidityMapperFast agent instructions

## Language and checking

All authored application code, scripts and tests are strict TypeScript: `.ts`/`.tsx` (browser, shared) and `.mts` (Node ESM). Keep the three compiler projects strict (`tsconfig.json` browser+shared, `tsconfig.node.json` server, `tsconfig.tools.json` scripts and tests); do not enable `allowJs`/`checkJs`, add blanket `ts-nocheck` or broad `any` casts. Type annotations do not validate exchange frames, HTTP bodies or storage: validate at those boundaries at runtime.

Permanent non-TypeScript exceptions: generated build output (`dist/`, `build/`), the generated WASM glue in `src/app/wasm/`, and the Rust kernels below.

## Rust/WASM compute kernels (approved exception, 2026-10-04)

Compute-bound inner loops (heatmap rasterisation, level grouping) live in `crates/hlm-kernels`, compiled to WebAssembly with wasm-bindgen. Rules:

- Kernels are pure functions over flat typed arrays; JavaScript owns all state, validation and I/O. A kernel holds no state between calls, touches no DOM and parses no exchange frame.
- Every kernel has native `cargo test` unit tests (`npm run test:wasm`) and a Node contract test (`tests/app-client.test.mts`) that loads the committed wasm and checks it against the server's JS implementation of the same spreading.
- Build with `npm run build:wasm` (needs the `wasm32-unknown-unknown` target and `wasm-bindgen-cli` 0.2.129). The generated glue and `.wasm` in `src/app/wasm/` are committed so a checkout builds without a Rust toolchain; regenerate whenever the crate changes.
- The crate keeps its default `crates/hlm-kernels/target/` (gitignored); create no other Cargo target directories.
- Do not add WASM for work that should not run at all. Memoise or delete first; profile before and after and record the numbers in `Research_Findings.md`.

## Performance and memory

The earlier byte-accounting "admission/lease/grant/reservation" machinery was measured as the dominant CPU cost on both client and server and was removed (`Research_Findings.md`). Do not reintroduce per-message or per-frame memory estimation, cross-tab byte leases or response-size reservations. Bound memory structurally: ring buffers, fixed retention windows (`RETENTION_MS` in the recorders), capped frames.

Measure with an isolated, visible-state headless Chrome over CDP. A tab reporting `visibilityState: hidden` has throttled timers and rAF; its numbers are meaningless. Use the real GPU path for WebGL timings (software GL says nothing about GPU frame time).

- A feed restart must never leave the server without feeds. `LiveFeedManager.start()` retires every old feed before its metadata requests, so an error in between used to leave a running manager with no feed and nothing to reopen one (12 hours of frozen candles and seven stopped venues, 2026-10-06; `Research_Findings.md`). `start()` now schedules a recovery with the last configuration that finished, a watchdog (`checkLiveness`) catches a start that hangs or a manager with specs and no feed, and `/api/diagnostics` reports `feedManager`. Keep new work between retire and open inside that guard, and keep recovery and watchdog timers `unref`ed.
- **The history store (`history.sqlite`) has a hard 224 MiB budget and refuses every write while its file is over it.** `npm run dev` runs HyperTracker in mock mode, and its made-up layers once filled the budget in six days (206 MiB of 224, 2026-10-11): candles and open interest stopped being saved for hours, silently. Mock layers are never written (`recordLayer`), ones an older build wrote are deleted at start with a compaction (`#dropMockLayers`), and a VACUUM is followed by a TRUNCATE checkpoint so the file shrinks at once (in WAL mode it shrinks only when checkpointed). Anything new written there needs a size that stays well inside the budget.
- **Stop serving before closing a store.** `server.close()` keeps a connection that is still busy (a large response draining, a body being read), and the page sends its next request on it once that ends; at a restart those requests reached the closed history ("statement has been finalized" on /api/v2/oi). Shutdown and a failed start call `app.stopServing()` (close, then `closeAllConnections`) before `v2.close()` and the history store, and a failed start closes v2 so the process exits (`tests/startup-process.test.mts`).
- **Zoomed out over days** (`Research_Findings.md`). The server merges minute columns into wider windows in flat arrays (`mergeWindow` in `shared/recorder.ts`, equal to the old map merge to the last bit; keep the test) and keeps windows that have ended; the page asks for column steps that double (`hub.loadColumns`) so zooming reuses them, and its 30 s refresh asks only for the windows that could still change (from `settledBefore` of the last answer; the worker splices them in with `withTail`): never ask a source for a whole window again on a clock. A merge on the request path blocks every other request: measure one before adding it. Anything a pane asks the worker for is keyed by what changes its answer, never by the view to the millisecond (a map following the live edge moves every frame): the depth pane counts whole columns (`depthKey`) and refreshes what is live on a clock, the raster is redone no more often than three times its own duration. A frame that only moves the pointer must not judge or regroup data: absorption keeps its judged marks until the groups or thresholds change and its squares until the map moves a pixel. No blurred shadow drawn per item per frame (the whale glow is a cached image, `glowOf`).
- **Older history from disk** (`Research_Findings.md`). The server holds `HOT_MS` (24 h) of depth columns and footprint rows in memory (a footprint minute's sums and statistics for the week) and reads older ones back from SQLite by the hour when a question reaches them (`ColumnStore.range` / `extent`, `FootprintStore.range`); a recorder whose store cannot read back (the browser) keeps its whole retention. A column or minute leaves memory only once the store has it, a late trade or order for a minute only the store holds reads it back into memory first (`#rowsToChange`), and an hour read back is kept only when it can no longer change and goes at the retention cutoff. Whatever a recorder keeps for the next question goes in a `KeptCache` (`shared/kept-cache.ts`): it never lets go an entry asked within 45 s and makes room in one go. Letting the least recently asked go one at a time kept nothing of a view wider than the cache (the page asks its whole window every 30 s, so each window went just before it was asked again) and cost 20 µs a window, since a `Map` walked from its oldest entry steps over every entry deleted since. Measure the first look after a start and the refresh separately, with a clock that moves.

## Phones and tablets

- Two attributes on `<html>` (`src/app/device.ts`, tested in `tests/app-device.test.mts`) drive the touch arrangement: `data-layout` (`phone`, `phone-landscape`, `desktop`: how the panes are arranged) and `data-bar` (`compact`, `full`: how the controls are). Put mobile CSS in `src/app/mobile.css` under one of them (or `(pointer: coarse)`), never in a user-agent test, and keep the desktop rules in `styles.css` unchanged. Script that must differ reads `isPhone()` / `compactBar()` / `isCoarse()` from the same module.
- A phone must not write the desktop's saved layout (`hlm-layout-v2`): `Layout.#persist` returns early when `isPhone()`. The dock's own sizes use `hlm-dock-size`.
- **First-visit defaults** (Karl, 2026-10-17). No pane under the map is on (`DEFAULT_SHOW` in `store.ts`: Depth, Open interest, Delta, L/S, LT and the Footprint's bar stats are each one switch away); the flow column and the book are. The two columns begin at the golden section of the window (`defaultColumns` in `layouts/layouts.ts`: the map keeps 61.8 %, each column 19.1 %, never under the 300 and 420 px they began at), and `main` in `styles.css` says the same with `max(420px, 19.1vw)`, so they follow the window until a column is dragged: `Layout` saves a width only for a column sized by hand (a saved 420 or 300 is the old default, not a drag). The page saves its whole settings on any change, so a default that changes is also written down in old saves: `DEFAULTS_REV` marks the revision the save was written under, and a save from before it with Depth and Open interest both on (the old default) has them off once. Any later default change of that kind needs the same: a new revision and a rule for what counts as a choice.
- Touch gestures come from the pure recogniser in `src/app/touch.ts` (tested with a fake clock); panes bind it with `bindTouch` and leave mouse and pen to their existing handlers. A pinch is reported per axis (`axisPinchScale`).
- Test by emulation: Chrome over CDP with `Emulation.setDeviceMetricsOverride { mobile: true, deviceScaleFactor: 3 }`, `Emulation.setTouchEmulationEnabled`, `Input.dispatchTouchEvent`, and `Emulation.setCPUThrottlingRate` for a slow phone. Check portrait, landscape (844 x 390), a small phone (360 x 640) and a tablet (820 x 1180 and 1180 x 820). It is Chrome, not Safari; say so when reporting.
- Never let a floating panel, menu or dropdown rely on `position` computed from its anchor on a touch screen: they are bottom sheets there (`ui.ts`, `menu.ts`, `sheet.ts`).
- **The Tape tab** (`panes/candle-pane.ts`; `candle/model.ts`, pure and tested; `candle/trail-gl.ts`; its id stays `candle` in the dock and `hlm-candle-v1` in storage) is a phone tab that fills the area in place of the map, and the tab a phone opens on (`defaultTab` in `dock.ts`, applied while no tab was ever tapped and judged by the layout the window is in NOW, so a browser's phone view opened from a desktop-sized window gets the Tape too; the key `hlm-dock-tab-v3` is new with that choice, so a phone that kept the Map opens on the Tape once). It is one continuous tape of every trade since the page opened (`TapeTally`, per market at a tenth of the map's grid step, its rows grouped at the view's step), fed from the dust's tape ring as it fills whether the tab shows or not (a phone always asks for the ring: `tapeWanted` in `main.ts`). Nothing is fetched and nothing restarts it: no timeframe, no recovery, no bar that resets (Karl, 2026-10-17: a one-minute candle that keeps resetting kills the flow, and the tab must open at once). The header is one slim row, the readout and help: since when, how many markets, and the minutes missed while the page was hidden (a background phone gets no trades; gaps over 5 s count); its choices (Look, Trail, Glass, Rows, Pulses) are a Tape section of the phone's Settings (`settingsFields`, hosted by `toolbar.tapeFields`), never in the header. The live book is either side as one silhouette per side (one faint fill under a crisp outline: venue pieces read as two tones of one book, Karl 2026-10-16), with an arrival rail and the trade trail behind it: every order of the window at its exchange time and price. Settings live in `hlm-candle-v1`, never in the page's saved state or layouts. Flashes on the rail are timed by arrival, the trail by exchange time. Buys are filled and sells hollow in every look, so the side reads without colour. Exchange marks go only on orders from the Bar stats' whale size up and on the largest flashes. Glass (`glass`: off, panes, bricks) is three pieces welded together over the trail, the bid book, the tape and the ask book (bricks: glass only inside each row's bar), drawn in WebGL from an off-screen copy of the trail blurred at a quarter of its size, never with `backdrop-filter`. On glass the book's fill is the shader's, from per-device-row data (`setRows`), so a row's pulse can brighten or dim it; with glass off or no WebGL the page's canvas draws it. Rows show their winning side more strongly the more it won (`rows`: glow, lean, delta; `rowEmphasis`), and resting liquidity added or pulled pulses its row (`pulse`: pressure, deposit; `PulseTracker` holds Astra's rules: a change counts only past the side's noise and on two frames, a row a trade reached is marked traded, a removal the price passed with no trade there is not called a pull, and a gap of more than two windows starts it afresh); a stack sends a shock out along the bar and a pull one back in. Orders of $25K and up (coin-scaled) send a wave from the rail through the glass (`glass/waves.ts`, the page's glass's wave field, an instance of its own): the panes are glass to it and the welds walls. `?rows=`, `?pulse=`, `?glass=` and `?style=` set and keep a look from the address. The trail is one animation loop near 60 fps that stops when nothing moves, waves included (1 fps with reduced motion), and the map's heat and the ladder are suspended while the tab covers them (`coverPanes` in `main.ts`): a Pixel 10 drew about 5 fps while the trail waited for a moved pixel and the hidden panes kept rendering. Nothing is drawn, asked or timed while the tab is hidden. The trade recovery the Candle tab used to ask for (`shared/recovery.ts`, the coverage record) stays for the browser engine and the footprint; the tab no longer asks for it. The design history is in `Research_Findings.md` (the Candle debates of 2026-10-16, superseded by the tape on 2026-10-17).

- **Volume profile (the traded column) and its levels.** Volume profile is a lamp button, off by default (`show.traded` is its switch; a save from before it had settings reads as off), whose panel holds `state.traded` (`readTraded` checks a save field by field). The option sits above both the Column and the Lines on the chart sections of the panel. An answer from before its window ended is not drawn for it, and a line runs no further than its source's `asOf` (candles: `heldTo`). `candles` is one market's candles (`profileTarget`: the most traded that lists the coin, Binance's perpetual first, whatever the chart shows), five-minute ones (one-minute for a session off the five, `candleBarMs`) up to twenty weeks back (`hub.profileHistory`, `PROFILE_CANDLES_BACK_MS`), each bar's volume spread evenly over its range (`candleLevels`): an estimate, labelled ≈ (measured 2026-10-18 against six recorded days of Binance BTCUSDT: VAH and VAL mostly within 0-2 rows of $20, but VAL 4 rows off one day and 10 on a day recorded at 96 %, and the POC on the other of two near-equal peaks up to 8 rows off; `Research_Findings.md`). Either way a window is drawn only when its source saw `DRAWN_SHARE` (nine in ten) of it, never faint. Sessions are wall-clock times in their zone and follow its daylight saving (`sessions.ts`, tested on the change days); a naked POC is judged on the chart market's candles with half a row of tolerance. The lines use the palette's `poc` colour (every theme has one), over a halo.

- **The columns' measures** (`measures/defs/`, `hub.ensureProfile`, `sideColumns` and `priceQuestions` in `heat-pane.ts`). Each column is `TRADED_W` wide; the map keeps half its pane (`COLUMNS_FIT`, both sides together), so a narrow one draws only the nearest that fit (`gutter` and `leftGutter` count them). Each adds up, over the same window (what is on the chart, or the day, week or session `Worked out over` picks), its own `ProfileAnswer` whose two sides take the bid then ask places, so the bars, POC, value area and hover read them unchanged; the hub asks and keeps each measure apart (`MetricColumn`), each answer carrying the window's `tag` like volume's. The lines on the chart are traded volume's when it is drawn by price on either side, else the first measure drawn by price, and a non-volume one draws only its own levels over that window (past days, weeks and sessions stay traded volume's, and the panel says so). Absorption: `markedPart` of each group at the threshold the Absorption settings judge it at, counted once (the marks' minutes are loaded for it even with the marks off). Liquidations: the source's record (its largest 5,000 when more match: the header says "the largest 5,000"). Open interest (`shared/oi-profile.ts`, `/api/v2/oi-profile`, the engine's `oiProfile`): each perpetual's change between consecutive one-minute bars, put in the minutes after the first reading up to the end of the second, spread over the prices that traded on that market in them by their share of the USD (`FootprintRecorder.spread`), linear markets in coins valued at each row's price, inverse ones (`inverseOiId`) in their own USD; increases and decreases apart, each venue on its own. A change across readings over `OI_GAP_MS` (an hour) apart, past the window's edges, or over minutes with no trades recorded is `unplaced` (signed USD), never spread elsewhere; the header says it when over a hundredth of what was placed. It is an estimate of where exposure grew or shrank, never of who or of entry prices: never call it new longs. A header sub-line in amber is a cut or incomplete record.
- **Order counts by price.** The footprint recorder counts each market order in the row of the price it started at (a buy's lowest fill, a sell's highest) in minutes begun since counting began; such a minute is stored as five numbers a row, an older one stays uncounted (three numbers), and an order never makes a row without volume (`nearestCell`). Keep `profile` and `query` answering three numbers a row: open pages parse those strictly.
- **Order sizes as settings.** Every size a person sets (retail and whales in the Bar stats and the dot rows, the smallest bubble and liquidation, the Liquidity Tracker's Min and Max) is any value, typed or picked from a menu (`sizeRow` / `sizeControl` in `ui.ts`, `takeSize` and `parseSize` in `sizes.ts`), saved as BTC's dollars and scaled for the coin. The recording keeps each minute's market orders from $25K one by one beside the size boxes (`TradeStats.big`, signed USD, the stored stats' optional sixth element), so a line can be drawn at any size from there: the footprint and sizes questions take up to four `cuts` and answer `over` only when every minute they count has its list. Minutes recorded before the lists are filled in from the prints after startup, in memory only. A page asks only for lines between box edges (`linesToAsk`: at an edge the boxes are exact, so the defaults send the requests they always did); where `over` is missing (an older server, minutes not filled in yet) it takes the nearest box edge and marks the row "≈". A saved box number from before reads as its edge. The whale VWAP's four sizes are the in-memory bands of `shared/print-sums.ts`, not lines.
- **Liquidations.** Only Binance (`forceOrder`, its own socket in `Made.liquidations`, at most one per symbol a second: `throttled`), Bybit (`allLiquidation`), OKX (`liquidation-orders`, every swap on one channel, filtered by instId) and Deribit (the `liquidation` flag on its trades) publish them; Hyperliquid, Coinbase and every spot market publish none, and `LIQUIDATION_COVERAGE` in `shared/liquidations.ts` is the one table of that. The side is the position closed (`long` = the exchange sold), read per venue (Binance's order side is the opposite of Bybit's position side; Deribit's M/T flag says whether the maker or the taker was forced). Bybit reports the bankruptcy price (about 0.3 % past the mark on BTC), which the market need not have traded at, so a `bankruptcy` report is drawn at the instrument's last trade if that came within a minute of the liquidation's own time (a report can arrive minutes late: then at its own price, and the box says so), and the box gives both prices. OKX calls its price `bkPx`, but it was measured within a few basis points of the mark, so it is a `fill` like Binance's and Deribit's, drawn where it went. For this the last-trade maps (`lastPrice` in `api.mts`, the engine's `#last`) keep each trade's own time. The server records them from $100 for a week (`liquidations` table, `/api/v2/liquidations`, pushed as `liquidations` on the socket) even for a venue whose book a browser reads, so FlowSources runs a covered venue's liquidation feed alone; the browser engine keeps them in memory only and the panel says so. What a venue does not report is said in the panel (`coverageLines`), never on the chart. A liquidation is also one of the market orders, so the Range line gives its share of all the market volume in the selection's minutes (not of a box's band: it is drawn at one price but traded wherever the book took it) and never adds it; it counts only those from the panel's smallest, and a fill that closed a long and a short (Deribit's MT) once in the share. A selection's panel reads what the map holds again (`refreshHeld`, no new recording question) when the large orders or liquidations arrive or their settings change. Diamonds in the sell colour for longs closed and the buy colour for shorts, as everything else on the page: the shape and its hard edge say forced.
- **Live trades (the trade dust)** (`shared/tape.ts`, `app/tape/`: `ring.ts`, `gl.ts`, `trace.ts`; `Research_Findings.md`). Every market order, as the recorders rebuild it from fills (`OrderBuilder.drain`, the same orders the bubbles are, so a venue that reports every fill does not look busier than one that reports one row per taker), is pushed as it completes in a binary `tape` frame (`encodeTape`, columns plus `seq` and `dropped`) once a pass (250 ms) to a page that asked for it with `{t:'tape',on}` on the socket (an older page never asks and is never sent one, since it reads every binary frame as levels), never skipped for a backlog (`sendVerdict` in `server/v2/backpressure.mts`: it was skipped from 2 MB queued while the 430 KB levels frames, 1.5 MB/s, kept coming to 4 MB, so a stall of a few seconds cost 19 batches of about 1 KB and left holes in the dust, probe 2026-10-19; now only the levels are skipped, from 4 MB, and a client more than 16 MB behind is dropped and reconnects); the browser engine posts the same batches (`onTape`, transferred). Nothing of it is stored anywhere: the page keeps a ring of 2^21 orders (2^19 on a phone; 6 floats each, times and prices relative to bases so a float32 holds them, `TapeRing`) and a reload starts empty; an order timed more than six hours from the page's clock is left out (`CLOCK_REACH_MS`: a bad stamp would rewrite the ring on every batch). A batch that is missing (`seq`), trimmed (`dropped`, more than `TAPE_BATCH_MAX` in a pass, the largest kept) or on a new connection starts a new segment, and the map draws where the live trades begin and each gap the price line breaks at (`gapMarks` in `tape/trace.ts`: a stretch no segment covers (their ranges merged, since exchange stamps overlap) of at least ten seconds and three columns, one column past the line's own break, so a mark is always a break and a break can go unmarked; a skipped 250 ms pass of a page that is behind starts a segment too, but no one can see that hole, and a full-height dotted line for each buried the map in them, Karl 2026-10-19). The dust is its own WebGL2 canvas between the heatmap and the overlay: each order a point sprite (log-scaled 0.75 to 2.2 CSS px for the coin's $100 to $250K, with a hairline over the prices an order walked, at most 48 device px either side: a sprite is never larger than 97 px, since one as tall as a long walk at a deep zoom costs the card a quarter of a million pixels an order) added into a float picture of buy and sell USD per pixel, shown in one pass (colour of the side that traded more, opacity by the log of the volume against the coin's fixed sizes, never the largest in view). Only orders in a block of the ring whose times reach the view are drawn (`runs`). The float picture is wider than the screen and shown shifted by whole pixels, so following the live edge only adds new orders (about 1 ms on an RTX 4070 with 2M orders held); it is redrawn whole on a zoom (2 to 13 ms). Arrivals redraw the dust canvas alone (`tapeArrived`), never the overlay; the arrival accent is the only animation, about 30 frames a second while one fades, none hidden or with reduced motion, and the dust is off in replay. While it shows, candles are hollow (outline and thin wick) and the chart market's price line (`TraceIndex`: each pixel column's first, extremes and last order by exchange time, breaking after ten seconds without one) runs over them, dashed from its prices a second (`FlowSeries.ownPrice`, never carried forward) before the page held orders; Venue lines adds every other market's, faint. The switch is the Trades panel's Live trades row (`BubbleSettings.live`, on by default, inside `show.bubbles`). The server's `state.trades` list is capped at 5,000 rows a pass: a burst beyond that is lost to the dust as it is to the flow and the footprint.
- **Key levels.** The previous day's, week's and month's high, low and middle, each period's open and the high and low so far of the one under way, as lines (`src/app/keylevels/`, off by default; the button is "Key levels" because the order book already has a Levels view). They are worked out from one market's candles read straight from the exchange (`fetchCandles` and `webGet` in `shared/history.ts`, the same in server and browser mode): the server's candle route serves only its own recorded minutes, capped at 400 bars. The candles are hourly, or half- or quarter-hourly in a zone whose clock is that far off the hour (`barMsFor`: India, Nepal, Lord Howe's summer), so every period starts on a bar and none is split. The market is the chart's own where its history can be read (the same instrument: OKX spot under `okx` is not the OKX swap), else the first of a fixed list that lists the coin, and the panel names it (`historyTarget`; a server names Binance spot `binance:BTCUSDT:spot`). `KeyLevelHistory` holds one stretch of bars, reaching back at most `MAX_BACK_MS` (62 days, so the previous month is always held; up to 24 pages a request, which OKX's 100-bar pages need), extends it back only when the chart needs earlier periods, in turns of at most 24 pages while each turn gets older bars, and stops once the exchange has nothing older, asks again for the newest bars every five minutes (`heldTo` is where the last such answer reached), drops bars older than the levels can reach, and waits a minute after a failure; nothing is asked or worked out per frame (the pane keys its caches by the view's hour and the clock's minute). A period's open is drawn when the history held reaches back to its start, and its high, low and middle only when it also reaches its end (`heldTo`, or the chart's own candles running on to now): a missing bar inside it is an interval nobody traded (Coinbase sends none), not a hole, but history that stopped at noon is not a day. After the last bar the chart's own candles (same market, no coarser than the bars) move the period under way. Days and weeks start in the Volume profile's zone (`traded.zone`, shared on purpose so the two never disagree), weeks on Monday, months on the 1st (`monthWindows`). A period's level is drawn only when its candles are complete; a previous level the next period never traded through runs on, dotted, until reached, and once its own period has ended its label carries that period's date and its axis tag is outlined and gives way to the current ones. Tags are placed (`placeTags`) clear of each other and of the live price's tag, never moved off their price, and a grid price under a tag is left out. The colour is the palette's `level` (every theme; the contrast test covers it). The names at the lines' right ends (the Volume profile's, the key levels' and the VWAP's) share one `LabelBoard` a frame (`labels.ts`, tested), claimed in paint order: the Volume profile's first (its lines have no tag on the axis to fall back on), then the key levels', then the VWAP's; a new feature that names its lines takes the board rather than keeping a list of its own (a point of control and a previous low at one price were printed over each other, 2026-10-18). The levels' arithmetic was checked against the exchange's own daily, weekly and monthly candles in UTC (Binance USD-M BTCUSDT, 2026-10-18): every high, low and open equal.
- **VWAP.** The session VWAP (restarting each day, week or month in the shared zone, with optional ±1σ/±2σ bands) and up to four anchored VWAPs a coin (`vwap/`, off by default) are each bar's typical price (high + low + close) / 3 weighted by its volume in coins (every venue's candle volume is in coins; checked for Deribit's inverse perpetual too), from the same market and the same loader as the key levels (`historyTarget`, `KeyLevelHistory` with a one-minute refresh, one instance per bar size: `hub.vwapHistory`). The bar size follows how far back the line reaches (`vwapBarMs`: a minute for a day, five for a week, half an hour beyond) and is never coarser than `barMsFor`, so a session never splits a bar. After the last bar the chart's own candles replace the partial one (same market, no coarser), so no volume counts twice. A session or anchor whose start the history does not reach yet is not drawn rather than drawn wrong; the line begins at the first bar with volume. Anchors are placed by arming the panel's button (`vwapAnchoring`, not saved) and clicking the map; that and the Range tool both take the next press, so arming one ends the other. Their tags go into the key levels' one tag placement (`KeyTag.color`), the session's ranked with the previous day's levels. The colour is the palette's `vwap` (every theme). The whale VWAP (buys in the bid colour, sells in the ask colour, no axis tags) is Σusd / Σcoins of the recorded large market orders (the prints: orders rebuilt from fills, the same as the bubbles) from a size band up, on the flow column's instruments, since the session began or the recording did (the panel says which). Its sums are kept in memory per instrument, minute and disjoint size band (`shared/print-sums.ts`: $100K, $250K, $1M, $5M, BTC's, scaled with the coin), fed by `PrintStream.ingest` after its deduplication and built once from the store when the stream starts (`PrintStore.each`: about two seconds for a week of BTC from $100K, before the server listens). Asking SQLite for the sums per request took 90 to 400 ms for a day and 1.7 s for a week at $25K (measured on the live recording 2026-10-09); do not add a size index to the live prints table instead: building it locks a 600 MB database for seconds, and it helped only from $1M. `/api/v2/print-sums` takes a band edge as `min` (400 otherwise); the page asks again every 45 s for whole minutes and adds the orders pushed since to the minutes after them (`hub.whale`), so none counts twice.
- **Coverage and trade recovery** (`shared/coverage.ts`, `shared/recovery.ts`, tested in `tests/shared-coverage.test.mts` and `tests/shared-recovery.test.mts`; `Research_Findings.md`). The coverage record tells a minute recorded with nothing in it from a minute nobody recorded, per instrument, minute and metric: trades by stretches open while every connector carrying the instrument's trades is live and the loop runs without a gap (`MAX_PASS_GAP_MS`: a frozen page runs no pass; a trade arriving after a missed beat closes the stretch and joins none), a failed feed cut back to its last message, each stretch with its first and last trade (the seam); depth from the depth recorder's own sample counts (`DepthRecorder.samples`), never kept twice. Stretches are stored in IndexedDB (version 4, `coverage`) and SQLite (`coverage`), cut at the minute still open except on the last flush, because the recorders store a minute once it has ended: a stored stretch must never claim trades that were not stored with it. `DataSource.coverage` answers it (the browser engine's `coverage` call, `/api/v2/coverage`); a source without it judges nothing. Recovery is the browser engine's alone (`DataSource.recover`; a server records whether a page is open or not): on the Candle view's open and on return from the background it fills the gaps of the bar under way, then the bar before, from the venues' trade REST (Binance USD-M and spot forward by id or time, OKX, Bitget and Coinbase back by id, Bybit and Hyperliquid their latest page only; Deribit and MEXC none), never through the live trade callback: rows in exchange-time order per instrument, between the seam's trades (by id where a venue's ids rise with time), orders rebuilt by a builder of their own, applied in one step with the stretch they cover (`#applyRecovered`: footprint, flow, size statistics, prints with `fresh` false; not the price, the candle, the trade dust, the live order builder or absorption). A gap is never recovered over minutes held from storage without a stretch (`trimUnknown`: an older build recorded them, and their trade ids are no longer known). One action is bounded by `RECOVERY_BUDGET` (20 pages, 20,000 rows, 30 s, two requests in flight); pacing, a failure and the minute's rest after it go by the venue's limit (`HistorySource.bucket`, the endpoint: OKX's swap and spot share one, and paced apart they once went over it together), never by market; what an action does not reach stays a gap, visibly. Verify a venue's limits before adding it.
- **Footprint markets and loading** (`Research_Findings.md`). `state.footprint.markets` is `'all'` (the default since 2026-10-13, Karl's choice) or `'chart'` (the chart market alone). `'all'` is the markets of the ALL VENUES lines (`aggregateIds`, as the Delta pane), sorted and joined with commas into the footprint's one `inst` (`HeatPane.footprintMarkets`); the route, the browser engine and `FootprintRecorder.queryMany` add them together on one grid. The bar statistics read the same data, so they follow. `FootprintData` never asks for a whole window on a clock: a settled bar (ended `FOOTPRINT_SETTLE_MS` ago by the source's clock, `hub.sourceNow()`) is kept, every `FOOTPRINT_REFRESH_MS` only the bars from there are asked for, and a window comes in slices of at most `FOOTPRINT_BUDGET` instrument-minutes, newest first (a minute read back from the store counts four), each answer saying with `from` where it starts. Settled bars that came without the sums of the size lines asked (minutes whose lists the server fills in after it starts) are asked again once a minute, at most ten times a load (`redo`, going on at once through the slices a budgeted answer leaves), and every five minutes the refresh reaches back an hour into the settled bars for trades a venue sent late (`RECHECK_MS`), a view that ends in that hour included even with no bar still under way in it (panned a few minutes behind the live edge), from the start of the bar that hour is in (on 4 h and 1 d bars an hour back is inside the bar before, and an answer's bars that start before where it was asked are not taken). One question for a week of hourly bars of 14 markets merged for 8 s on the server's only thread; a slice is at most about 200 ms. Bars of whole hours read each instrument's ended hours added together (`FootprintRecorder.#hourRows`, `Research_Findings.md`: zooming out over six days of 13 markets was 129 answers, a repeat 129 again; now 17 the first time and one after): an hour is dropped when a minute of it changes (`#rowsToChange`) and at the retention cutoff, and the route `prepare`s the hours an answer reads first, a few at a time with the event loop let go every 8 ms, the newest bar always whole (a daily bar is never merged minute by minute in one go). In the budget a held hour costs 2. The traps stay the chart market's (they are judged on its candles). With markets added together each row also carries every market's part: the page asks with `venues=1` and the answer adds `venues` and per bar `venueRows` ([place, buy, sell, ...] per row), which `readBar` turns into ids (`parts`), since one view's slices come in answers with their own order; a malformed one is left out whole. The row's bar is drawn as the venues' pieces of its volume (`barPieces`, the Compact book's, in one order per load, `venueOrderOf`; shade alternating by place, narrow ones joined at the end), filling the bar as drawn whole, with the venue's mark in a piece wide and tall enough and never over a printed number; the row's popup lists its venues (eight, then the rest). Venues cost 2.2 to 2.7 times the answer; the worst slice went from 197 to 212 ms (measured 2026-10-13).
- **Open interest added together** (`Research_Findings.md`). `state.oiMarkets` (`'all'` by default, the OI pane's Venues select) adds up the perpetuals of the ALL VENUES lines on a venue whose open interest is read (`oiVenueIds` in hub.ts: Binance, Bybit, OKX, Bitget, Deribit, Hyperliquid, in coins); the hub asks for each venue's bars on the existing one-market route and keeps them as `state.oiParts`, `state.oi` being their sum; a load for the same markets still under way is reused rather than superseded by the 10 s clock (a slow history would otherwise never land). The one definition of a bar's change is `oiChangeByTime` (oi-change.ts): with parts, each venue's own change from the bar one timeframe before, over the venues present at both, never the difference of two sums (a venue whose readings start would show its whole open interest opened); a venue without a bar is carried at its last reading for up to `max(2 timeframes, 10 min)`. The OI pane, the bar statistics' oi chg and the OI sound all use it. The OI pane draws its level, with venues added together, chained from those changes (`chainedOi`: it ends at the venues' total now and steps back by each bar's change), so it moves exactly as the bars below it do; the sum itself stepped wherever a venue's readings started (on the website most venues start when the page opens), a jump the bars rightly did not show (Karl, 2026-10-14). `state.oi` stays the sum. NL/NS reads each venue first and then adds them (`nlnsModel`, below). An inverse market (Deribit's BTC and ETH perpetuals, `inverseOi`) counts open interest in USD and its coins are the USD at each reading's mark, so a price move alone would read as positions opened or closed. Each reading keeps its own USD as `quote` (`fetchOiReading`; stored in `oi_bars`' quote columns, the browser engine's samples), `/api/v2/oi?usd=1` and `source.oi(…, usd)` answer that USD (rows without it left out; a server that does not echo `usd: true` is taken as having none), and the hub divides it by one price, the newest close of the candles on screen (`Hub.oiSeries`), for the pane, the sum and NL/NS alike, and keeps that price (`OiPart.usdAt`, `state.oiPrice` for one market) so a change in USD (the bar statistics' oi chg in USD, `oiUsdChangeByTime`) is its change in its own USD, not its coins at another candle's close; where no USD readings exist it falls back to the coins put back into USD at each candle's close (`atOnePrice`), which is off by the price moved between a reading and its candle's close. NL/NS takes bars a candle apart as consecutive readings on any timeframe (a daily chart's are a day apart), and works out one hold of candles before the view (`withLead`) so a reading's stretch that began before it is given to all of its takers. The server reads Binance's and Hyperliquid's open interest in the feed manager and the other four with `OiSampler` (v2/oi-sampler.mts, a live server only: `oiSampling`), once a minute while their book is live, Bybit's and OKX's history first, written straight to the history store; a page reads Binance's and Bybit's history and samples the six while it is open (OKX's history sends no CORS header). Bitget and Deribit have no history: their part starts when sampling does. Bybit's `openInterest` counts both sides of every contract (twice what the other venues report, 2026): its `singleOpenInterest` (and `singleOpenInterestValue`) is read, half the two-sided field where an answer has none, and what was stored before is halved once at start (`migration_state` 'bybit-oi-single'). Bybit's coin-margined perpetuals (`bybit:BTCUSD`, a server's `BYBIT_CATEGORY=inverse`) are inverse too: read in Bybit's inverse category with their USD as `quote` and `openInterestValue` as coins, and with no history (it is in USD, with no price to put it in coins at). The Long/Short reader reads a Binance COIN-M perpetual (`BTCUSD_PERP`) from the COIN-M statistics by its pair (its top positions come as `longPosition`) and a Bybit coin-margined one in the inverse category. OKX stamps a history row with the start of its period and the reading at its end (measured against live samples, 2026-10-14; Binance and Bybit stamp the reading's own time), so `fetchOiHistory` puts it at the end. A restart reads the history again over rows the store holds, which the store turns away: that is not a refusal (`oiHistoryWriter`: only a store that stopped writing is), or the read stops at its oldest row and the stretch the server was down is never filled in. Binance's poll (the feed manager's) reports its last outcome, failures in a row and a poll still under way in `/api/diagnostics` (`feedManager.openInterest`) and logs failures every ten minutes; every REST attempt has a deadline (`REST_ATTEMPT_TIMEOUT_MS`), since a request shares the flight of its key until that settles (the poll froze once with nothing saying so).
- **Footprint imbalances.** Footprint is a lamp button (it holds settings), no longer one of the pane toggles; its switch is still `show.footprint`, which also shows the bar statistics and their phone tab. Every row with volume has a bar as long as its volume (sold and bought) against the busiest row in view, on the panel's Bar width (`state.footprint.widths`, `barFraction`: in proportion, square root, the default, or logarithmic over four decades), in the colour of a side that traded at least 1.15× the other (`imbalance()`; the traps and the popup use it) and grey where neither did: a bar on imbalanced rows only left gaps that moved as zooming regrouped the rows (Karl, 2026-10-14); diagonal imbalances are a separate layer (`diagonalImbalances` in `panes/bar-stats.ts`: a row's sells against the buys one row up, its buys against the sells one row down, with the ratio; a row beside an empty one inside the candle counts only with `imbZeros`, past the candle's range never), outlined around that side's half of the row with the number bold, and named with its ratio in the row's popup. The ratio, minimum, `imbZeros` and stacked rows are `barStatOptions`, shared with the strip (both read the same `FootprintData` at its step, so they agree, and both change with the row size as you zoom); the footprint's own settings (`state.footprint`: text mode, diagonal, zones, naked points of control) are separate. The marks are worked out once a load (`FootprintMarks`, keyed by `FootprintData.version` and the options), never in the paint loop. Stacked-imbalance zones and untouched (naked) points of control run on from closed candles only (`footprint/runs.ts`: a zone until a later candle of the chart market trades into it, a point of control only while none has), drawn under the candles only while the footprint shows (faded with `lod.barAlpha`: its data loads zoomed out too) and when the candles are the chart market's own, at most 80, cached by the marks, the candles and the candle under way.
- **Delta pane.** A pane toggle (`show.delta`, off by default), not a lamp: it chooses what is shown; its header holds its settings (`state.delta`, `readDelta`). Each candle's delta is the taker buys minus sells in dollars over the instruments of the flow column's ALL VENUES lines (`aggregateIds` in `cvd/model.ts`, the function the column's aggregate uses, so the two agree), read from `FlowTrack.cumDelta` (seconds, while candle times are ms); the pane asks the flow book for a day of seconds and the minutes before them the way the flow column does. A market counts in a candle only when it holds the second before it, so none steps in halfway; a candle with nothing recorded is left out and the CVD starts again after it, since what happened in the gap is not known. A running delta cannot tell a stretch nobody recorded from a quiet one, so the gross volume decides (`FlowTrack.cumGross`, `unrecorded`): candles with no volume on any of the markets for ten minutes or more in a row (`UNRECORDED_MS`) are taken as not recorded, a shorter quiet stretch is a delta of 0 (a thin coin can go a minute without a trade). A CVD candle's open and close are exact, its high and low the running sum sampled `SAMPLES` (16) times through the candle (the extremes of a sum over several markets are not kept), and the help says so. Closed candles are worked out once (`FlowCache`, keyed by the instruments, the timeframe and `FlowBook.loads`, which every load, failure and invalidate bumps), never per frame. A daily or weekly restart uses the Volume profile's zone (`resolveZone`, `windowsOf`). NL/NS (`nlnsModel` in `delta/nlns.ts`, pure) takes the OI pane's markets (its parts with venues added together, else its one market), each with its own flow (never the ALL VENUES delta against one market's OI). A market's change is measured between its own consecutive readings no more than `OI_HOLD_MS` apart, shown in the candle of the new reading, and given to the side of that market's taker delta summed over every candle since the reading before (a sparse or hourly reading is marked `coarse`), only when its flow is recorded for every one of them (flow over part of the stretch, a start or a gap inside it, says nothing of the rest); otherwise the sign of the chart's close change over the same stretch (only when the chart's candles are that coin's own, never a borrowed reference series), and where neither can say, `unknown` ("side unknown", never "takers even"); recorded flow that came out even is `unassigned` (takers even), never the price's. Each market is classified into the four parts (`longOpened`, `longClosed`, `shortOpened`, `shortClosed`) before they are added, so new longs on one venue beside new shorts on another show as `mixed` ("Both ways"), not as no change; `longs`, `shorts`, `v = longs − shorts` and their running sums restart with the CVD's keys and after a candle no market covers (`heldOiAt`). In coins; the readout names the market or the venue count. The pane keeps the model (`#nlnsModel`) until its inputs change, and at most once a second for the open candle. `state.delta.nlns` (the header's As select, shown only with NL/NS) draws it as one net series (bars and `cum`) or split: `cumLongs` and `cumShorts` as two lines on one scale, named at their right ends (L and S). No divergences in that mode. - The order book's zoom is a price step per row (`panes/ladder-zoom.ts`, the `GROUPS` list: each step regroups the book 2 to 2.5 times). The wheel goes through `ladderWheel()` (at most four steps a second for clicks, three for a touchpad, one step per event however many clicks a browser folds into it: a free-spinning wheel or a long swipe once threw the zoom from 20 to 1000), and the wheel, a drag on the price column and the touch drag share one anchor rule, `holdsMark`: while the book is centred on the mark (and Alt is not held) a zoom holds the mark on the middle row and passes the mark as it is at every step, never the price captured at the start (BTC moves while the hand does); once the book is scrolled, or with Alt, it holds the price under the pointer. A new zoom input must use both.
- **Replay** (`replay/clock.ts`, `replay/bar.ts`). Two clocks: `pageNow()` is the display time (the view's now, candle ends, the countdown, key-level and VWAP periods, flow windows, the Volume profile's window), `Date.now()` the real time (what is loaded or cached, staleness, request windows, judged data such as absorption thresholds). New drawing code that means "now" takes `pageNow()`; loading code keeps `Date.now()`. The moving time lives in the clock module, never in the store (only the controls' view is, `state.replay`, never saved). Everything right of the moment is masked (the map's overlay and `TimePane`); what is aggregated over a candle or bar containing the moment would carry its future, so it is cut: the candles (`candlesAt`, the one under way rebuilt by `formingCandle`), the footprint (`until`), the bar statistics, the OI bars, the key levels' bars, the VWAP points. The ladder, the profile column, the dot strip, sounds and alerts are off in replay; a `replay` change redraws the panes (no new data need arrive).
- **Price line, countdown, Go to** (`price-line.ts`, pure and tested). The price line, its axis tag and the order book's price row take the candle under way's direction (`lineSide`; the plain ask colour without a candle or with a borrowed series), the tag text `textOn` (theme.ts). The countdown sits under the tag, or above it at the foot of the axis, inside the band `placeKeyTags` keeps clear; it redraws once a second only when nothing else drew the map for 900 ms (`heat.tick`, never a raster clock), and not on a phone. Go to reads a `datetime-local` on the page's clock (`parseDateTime`, both zones tested) and moves the map as a drag does (`heat.goTo`).
- **Saved layouts** (`layouts/`: `layouts.ts` pure and tested, `panel.ts`; the status bar's Layouts button). A layout is `settingsOf(state)` (`LAYOUT_KEYS` in store.ts, without the VWAP anchors and the Volume profile's zone) and `Layout.arrangement()`, kept in `hlm-layouts-v1` (at most 20, the same name in any case replaces). Every field of a saved page and of a layout goes through `readSettings` (store.ts), which checks each one, since a layouts file can come from anywhere: a new setting needs its check there. Applying arranges the panes first (`Layout.apply`, nothing on a phone) and then sets the settings, keeping the chart's own anchors and zone. Pane order goes through `arrangeOrder`: flexible panes (the map) keep their place, the fixed ones follow the saved order and a pane it does not name comes after them.
- **Keyboard shortcuts.** One table (`SHORTCUTS` in `src/app/shortcuts.ts`, pure and tested) and one listener (main.ts); the list (the status bar's Keys button, and `?`) is made from the table, so add a shortcut there and nowhere else. A key is left alone in a field, with a dialog open, once another handler used it (`defaultPrevented`: menus take Home and End) and with Ctrl, Alt or Meta held (browser shortcuts; AltGr reports Ctrl+Alt, so no shortcut may need a character typed with AltGr). Digits match by `code` (the 1 key on every layout), letters by `key`. Arrow keys are not shortcuts (selects, menus and pane grips use them), M is not one (the toolbar's Mirror is M), and a switch does not repeat while held. A key that switches a lamp feature redraws its panel if it is open (`toolbar.refreshOpenPanel`).
- **Far books** (`shared/far-book.ts`). A venue whose WebSocket stops near the price but whose REST book goes deep (OKX `books-full`, Aster depth 1 000) is read from REST every 15 s while its book is live and drawn (a page must also be shown; a connector run for its trades alone, `bookRead = false`, reads none), and those levels are used only strictly beyond the WebSocket book's deepest level on each side, as it is when valued, until 60 s old: the WebSocket book is the authority wherever it reaches. The connector merges them in `valued()`, the server in `refreshBooks` (`withFar`, its cache keyed by the far snapshot too). A venue whose WebSocket can send a deeper book takes that instead (Deribit's whole book, Kraken depth 1 000, Bitfinex `len` 250, HTX `step0`). **A session that keeps the whole book (Kraken, Bitfinex) changes only the levels each update names, in place, and hands the whole book on at most every `WHOLE_BOOK_EVERY_MS` (250 ms)**: an update in between is taken and checked (`held`, kept as `pending`) and goes out with the next one after the interval, or on a timer when none comes (`#scheduleWholeBook`). Kraken sends 100 to 250 updates a second; when its session copied, sorted and re-read the whole book on each and handed every result on (a book costs the server's state about 400 µs at 1 000 levels a side), depth 1 000 stalled the server for good (2026-10-12). Measure a feed's message rate and its per-message cost before deepening it. MEXC's deep REST book is left out on purpose: it is several times Binance's near the price on a quarter of the trading and would dominate the map (`Research_Findings.md`).
- Do not write the DOM on every pointer move unless the value changed: assigning the text a node already has still invalidates style and layout. Header readouts use `setHtml` / `setText`, which write only on change. Measure with CDP `Performance.getMetrics` (see `Research_Findings.md`).

## Running and verifying

- `npm run dev` builds and starts the live server on `http://127.0.0.1:8787` (a page it serves uses it as its data source); `npm run dev:client` runs the page alone, reading the exchanges from the browser; `npm run build:site` builds the static site; `npm run dev:fixture` runs offline. Before starting or restarting a local service, inspect existing process and port ownership; test on a spare `PORT` rather than stopping someone else's server.
- `npm test` builds and runs the Node suite; `npm run typecheck` runs the three strict projects; `npm run build` does both plus the Vite bundle.
- Visual inspection: compare against `example_images/` (a local folder that is not in git: reference screenshots for the heatmap, order book and footprint, plus `colour-ramp.PNG`, the reference for the colour ramp and the Liquidity Tracker row). Heatmap, profile, ladder and footprint spacing, intensity and grouping follow those screenshots.
